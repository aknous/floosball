# Floosball Backend

Football simulation engine with a FastAPI REST/WebSocket API, SQLAlchemy ORM, and SQLite storage. A background task simulates an endless league (seasons → playoffs → offseason → next season); users play a fantasy/cards/pick-em/GM metagame on top of it.

> **Keep this file current.** This is the source of truth for the backend's architecture, systems, conventions, and key constants. Consult it before changing code, and when a change alters something documented here (a system's behavior, the data model, an endpoint group, a constant's meaning, a convention), update the matching section in the same change. If you find a claim here that's wrong or stale, fix it.

## Quick Start
```bash
python run_api.py --fresh --timing=fast          # Fresh DB, instant sim
python run_api.py --timing=fast-catchup --fresh  # Fresh, backdate to last Monday, catch up instantly then go scheduled
python run_api.py                                # Resume existing season (default: scheduled)
```
API docs at `http://localhost:8000/docs`. Frontend repo at `../floosball-react/` (`npm start` on :3000, talks to backend on :8000).

## Coding Conventions
- Python methods/functions/variables: **camelCase** (not snake_case). No exceptions for locals.
- SQLAlchemy column names: snake_case (DB convention).
- Class names: PascalCase. Constants: UPPER_SNAKE_CASE. Private methods: `_prefix`.
- No emojis in UI strings — use SVG icons instead.

## Naming Philosophy
Mix of formal, pop-culture, and humor. No trendy internet slang. One-word names preferred; should sound good with suffixes (e.g. "-Pack"). Pack tiers use formal style. Card effects and achievement names can be playful (e.g. "Fat Cat", "Home Alone", "Scorched Earth"). Test: would the name feel dated in 20 years? If yes, skip it.
- ⚠️ **`"Firstname Lastname"` in `config.json`'s player pool is INTENTIONAL** (owner, 2026-08-09) — it is the joke, not a placeholder left in by accident. It reads like an un-substituted template, so it gets flagged as a bug on sight; it is not one. Leave it in the pool.
- **The player-name pool is `config.json`'s `players` array**, and it is the only name source a fresh database has. Names added later (admin portal, Discord `/name`) live in the DB — see `tools_migrate_names.py`, which folds a live database's names back into config before a fresh start. ⚠️ Reduce to the BASE name first: `seasonManager._recyclePlayerName` walks a retiring player's name up a ladder (Base → Jr. → III → IV → …) and returns the variant to the pool, so a DB holding "Freed Marinara Jr." is the same pooled name as config's "Freed Marinara". Seeding variants starts the pool partway up the ladder. Coaches draw from the SAME pool as players.
- ⚠️ **AT MOST ONE FORM OF A LINEAGE IS IN CIRCULATION AT A TIME**, enforced by `connection._normalizeNamePool` + a lineage-based (not string-based) comparison in `_seedUnusedNames`. A name goes up a rung precisely BECAUSE its holder is gone, so a base and its Junior are never both live; when they are, one is an artefact. Two sources, both fixed 2026-08-10: (1) `_seedUnusedNames` compared EXACT strings, so once `_recyclePlayerName` produced "Bob Jr." the pool no longer matched config's "Bob" and **re-seeded the base on every boot** — a fork per restart per generation, on a perfectly healthy long-running DB; (2) `clear_db()` preserves `unused_names` but drops every player and coach, so a variant left behind is a Junior whose father never existed in that league. Measured on the season-1 production DB: 712 pooled names, **39 variants** (32 with the base also pooled, 7 with the base worn), plus 10 players and 1 coach wearing one. Base names across pool+players+coaches came to **886, exactly config's 886** — nothing was ever lost, the pool was over-full rather than short. `_normalizeNamePool` deletes the duplicate and keeps the BASE, runs on every boot, and is a no-op on a legitimate recycled variant (base genuinely absent). `resetLadders=True` additionally collapses survivors to base and is for `clear_db()` ALONE, where the wipe guarantees no lineage has a living member. ⚠️ `tools_migrate_names.py` must also read **`pending_names`** (recycled names serving their `NAME_REUSE_DELAY_SEASONS` hold) — that table is NOT preserved by `clear_db`, so a name sitting out its hold at the wipe would vanish. Regression: `test_name_pool.py`.

## Key Systems

### Timing Modes (`timingManager.py`)
`TIMING_MODE` env / `--timing=` flag. 12 modes:

| Mode | In-game delays | Real-time scheduling | Broadcasting | Notes |
|------|----------------|----------------------|--------------|-------|
| `scheduled` | Yes | Yes | Yes | Production. Games at real-time schedule; polls until start. |
| `sequential` | Yes | No | Yes | Play-by-play delays, fixed week gaps, no wall-clock. |
| `turbo` | No | No | Yes | Short fixed pauses between games/weeks. |
| `fast` | No | No | Yes | No delays anywhere. Default for dev. |
| `demo` | No | No | Yes | Like fast, but visible offseason pick delays (5s). |
| `test-scheduled` | No | Yes (compressed) | No | Real polling, minutes apart, fast polls. |
| `offseason-test` | No | No | Offseason only | Fast silent regular season; interactive (compressed) offseason. `_isTestMode` (low GM quorum). |
| `catchup` | **Yes** | Yes (→scheduled once current) | Yes | Backdate to last Monday, catch up **with** play-by-play delays. |
| `fast-catchup` | **No** | Yes (→scheduled once current) | Yes | Backdate to last Monday, catch up **instantly**, then go scheduled. |
| `playoff-test` | No (reg) / polling (playoffs) | Playoffs only | Yes | Fast regular season + compressed scheduled playoffs. |
| `turbo-silent` | No | No | No | Sequential-ish week gaps, broadcasting off. |
| `fast-weekly` | No | No | Yes (game events suppressed) | Instant games, 30s between weeks, visible offseason. |

> `catchup` = delays during catch-up; `fast-catchup` = no delays during catch-up. (Earlier docs had these reversed.)

### Season Structure (`seasonManager.py`)
- **32 teams**, 2 leagues × 16, each league split into **4 divisions of 4** — 8 divisions total (owner, 2026-08-07; was 2 divisions of 8). Regular season = **28 weeks**.
- ⚠️ **`team.division` is PERSISTED** (`teams.division`, model + inline migration + load/save plumbing in `teamManager`, written by `_assignDivisions` immediately after stamping). It was in-memory only, so **every restart un-divisioned the league**: the standings board lost its DIVISION column and By Division view, `_applyDivisionSeeding` fell back to plain record order and division winners lost their guaranteed top-four seeds, `_awardDivisionTitles` had nothing to award off, and the contextual tiebreaker fell to league record for every tie. `_assignDivisions` only runs at schedule generation, so nothing re-ran to repair it until the next season.
- ⚠️ **League AND division membership are curated in `config.json`'s `teamDistribution`** (`{leagueName: [teamName, …]}`, owner 2026-08-09). `_distributeByConfig` adds clubs **in the order listed**, and `_assignDivisions` slices that order into fours — so one map sets both which league a club is in and which division. This is deliberate over reordering the `teams` array: **team id IS config position** (`_createTeamsFromConfig` increments it) and `patternType = (teamId - 1) % 32`, so reordering `teams` would silently reassign every club's MARK. It also works on an existing DB, where the config-order split does not (teams load in DB id order).
  - ⚠️ Colours do NOT work this way — they load from the DB (`team.color = db_team.color`), so a config colour change only reaches a fresh start. An existing prod DB needs a one-off update.
  - ⚠️ Divisions are positional on `league.teamList`, and `realignByRecentPerformance` REORDERS that list by win rate. If it ever runs, curated divisions become strength tiers. Currently inert: `league_realigned` is stamped and the stored alignment is a 24-team map that no longer covers 32 clubs.
- **Division names come from `config.json`'s `divisions` map** (`{leagueName: [4 names]}`), owner-curated like team names. `seasonManager._divisionNames` falls back to compass points if the key is missing, so a config without it still yields a division-shaped league rather than silently dropping to the flat round-robin. Assignment is **positional** — within a league, config-order teams 0-3 are the first division, 4-7 the second, and so on — mirroring how leagues themselves split by config order, so the owner controls division membership purely by ordering.
- **The 28-week divisional schedule** (`_generateDivisionalSchedule`): **12** division rivals (3 opponents × 4, two full home-and-away rounds) + **12** the rest of your league (once each) + **4** one interleague division = 28. Replaces the old 14/8/6 split, which only worked when a division held 8 clubs. Division share is 43% (was 50%). The second division double-round is placed **LAST**, so the whole final game day is against the clubs you are racing for the division title. Every club in your own league is played at least once — the wider-interleague alternative was rejected because it could only draw 10 of the other league's 16, which diverges strength of schedule. Verified: 28 games per club, **exactly 14 home each**, all 32 clubs playing every week. Regression: `test_divisional_schedule.py`.
- ⚠️ **`_crossDivisionWeeks` had a live home/away bug** fixed alongside this: the opponent index is `j = (i + r) % n`, and a mod-n shift preserves parity, so deciding home/away on `(i + r) % 2` meant division B only ever hosted when `j` was ODD — **every even-indexed club in B got zero home games** across the whole cross-division block, in the shipped 8-club format as well. Home/away now alternates on the ROUND, which is index-independent.
- **League assignment**: at boot `leagueManager.createLeagues` splits teams into the two leagues by **config order** (first 12 → league 0, next 12 → league 1) — the DB `team.league_id` is a mirror it overwrites each boot, NOT authoritative. **Exception**: a saved `league_alignment` app_setting (JSON `{leagueName: [teamId,…]}`) overrides that split (`_applyPersistedAlignment`) so a realignment survives restarts/deploys. **One-time competitive realignment** (`leagueManager.realignByRecentPerformance`, fired once by `seasonManager._maybeRealignLeagues` at a genuine new-season boundary before schedule generation): ranks all teams by combined win% over the last `LEAGUE_REALIGN_WINDOW_SEASONS` (2) completed seasons and serpentine-splits them (rank 1→A, 2→B, 3→B, 4→A, …) so neither league stays perpetually stronger. Gated by the `league_realigned` app_setting (never re-runs; stays unstamped if there's no season history yet, retrying next boundary). Validated: even split (each league ~0.50 avg win%, full talent spread).
- **4 game days** per "week index block" (days 0–3 from the season start anchor = Mon–Thu), 7 rounds per day, games on the hour 12:00–18:00 ET. Playoffs are day 4 (**Friday**); offseason drafts follow.
- Season start anchor: SCHEDULED → next Monday 04:00 ET; CATCHUP/FAST_CATCHUP → last Monday 04:00 ET.
- **Week rollover**: 15 min before game time for intra-day transitions; **8 hours early** (prior evening) for cross-day boundaries (week indices 8/15/22) so the next slate is visible the night before.

### Playoffs
- Top half of each league qualify (**8/league = 16 teams** at 32 clubs); a power-of-two field means no byes. With 4 divisions a league's 8 qualifiers are the 4 division winners plus 4 wildcards.
- **`_applyDivisionSeeding` delegates to `standings_view.seedLeague`** — the same function the standings board renders — so the seeds a fan reads all season cannot contradict the field that actually gets built. Two bugs it carried, both reachable only at 4 clubs per division: (1) it swapped each missing division winner in by dropping the LAST qualifier, which dropped the previously-swapped winner when a second was also missing, so the field came back one club short of the winners it claimed and `len()` landed on **9 instead of 8** — silently handing out byes via the power-of-two check; (2) the **eliminated set was the bottom half BY RECORD**, computed before division seeding, so a division winner finishing outside the top half was marked eliminated and dropped into the FA draft order while still alive in the bracket. The eliminated set is now the complement of the actual field. ⚠️ Earlier: the division check was hardcoded to `len(divs) != 2`, which dropped every division winner's guaranteed seed at 4 divisions; now `< 2`.
- **Winning a division is an honour**, recorded like a league title or Floos Bowl (owner, 2026-08-07). With 8 divisions it is what most clubs are actually playing for — 24 of 32 will never win a league title. Awarded at playoff seeding off the club's standing **inside its own division** (`_seedTeams` over the division members), not off the playoff field, so a club can win a weak division without being top-4 overall and still be champion. Stored as `team.divisionTitles` (`'Season N'`, mirroring `leagueChampionships`) + a per-season `divisionChamp` flag, persisted to `teams.division_titles` (model + **inline migration**, since alembic does not run on deploy) and to the `Championship` table as `championship_type='division'`. Announced through `leagueHighlights` + a `league_news` broadcast, and idempotent so a playoff resume cannot double-award. ⚠️ The four title types (`regular_season` / `division` / `league` / `floosbowl`) now persist through **one loop** over `TITLE_KINDS` — they were four near-identical copy-pasted blocks, which is exactly where a new title type gets half-added. Regression: `test_division_titles.py`.
- **Re-seeds every round** by the shared chain in `seeding.py` — highest plays lowest, not a fixed bracket. `seeding.orderTeams` is the single source of truth, shared with the standings board so the two cannot diverge.
- **The tiebreaker after win% is CONTEXTUAL** (owner, 2026-08-07): **division record** when every club in the tie shares a division (the division title), **league record** otherwise (the wildcard). Then score differential → head-to-head point diff → points-for → points-against. ⚠️ The switch exists because division record is only comparable between clubs that played the same slate — 12 of 28 games against the identical three opponents — so an 8-4 in one division against an 8-4 in another compares different opponents. A wildcard race falls to league record, which the clubs DO share a basis for (24 of 28 games are intra-league). A group of two from one division tied with a third from another is a wildcard comparison and uses league record.
- ⚠️ **PERSISTED to `team_season_stats.div_wins/div_losses/div_ties/lg_wins/lg_losses/lg_ties`** (model + inline migration + save/load plumbing, 2026-08-09). They previously lived ONLY in the in-memory `seasonTeamStats` dict with no column at all, so **every restart reset them to zero** and they re-accumulated from that boot onward — measured mid-season: **447 games played, 48 division decisions recorded**, i.e. the playoff tiebreaker was comparing whatever had happened since the last deploy. The increment logic itself was always correct (wins and losses summed equal). No backfill (owner) — a season already in progress carries whatever it has.
- Tracked as `divWins/divLosses/divTies` and `lgWins/lgLosses/lgTies` on `seasonTeamStats`, incremented at game end **and on the crash-recovery path** (which re-applies W/L by hand, so a crashed game would otherwise count in the overall record and vanish from the tiebreaker). Both compared as **RATES**, since clubs can reach a tiebreaker having played different numbers of division/league games. ⚠️ `team.league` is the league NAME (a string), not an object — reaching for `.name` yields None and every game reads as non-league. A division game always counts as a league game. Surfaced on standings rows as `division`, `divisionRecord`, `leagueRecord`. Regression: `test_division_record.py`.
- 4 rounds, named `Playoffs Round 1` (wk 29) → `Playoffs Round 2` (wk 30) → `League Championship` (wk 31) → `Floos Bowl` (wk 32). Rounds 1–3 are within-league; the Floos Bowl is the cross-league final.
- ⚠️ `seeding.buildH2HGames` was **deleted by the tiebreaker-split commit while both callers still imported it by name** — `/api/standings` returned 500 and `_seedTeams` raised (its import sits above the try/except meant to tolerate a missing h2h). Restored. If a seeding import ever goes missing again, check that commit's blast radius first.

### Standings Board (`standings_view.py`, `GET /api/standings`)
The board answers three questions off one payload — who leads each division, where does everyone sit, how close is the wildcard race.
- **`seedLeague(teams, h2h)`** → `{ordered, seeds: {teamId: (seed, kind)}, divisions: {name: [ids]}, recordRanks}`. Calls `seeding.orderTeams` and mirrors the division-winner rule; `_applyDivisionSeeding` delegates to it, so there is exactly one seeding implementation. Mid-season seeds are a **projection**, not a freeze.
- **Rows arrive in DISPLAY order** — qualifiers by seed, then the rest by record. Sorting by record makes the seed column read `1,2,3,5,6,4` (reads as a bug) and puts the cutline on the wrong row whenever a division winner has a losing record, which at 4 clubs per division is routine.
- **`gamesBackFrom(cutTeam, team)`** is signed from the club ON the cut: negative = ahead, `0` = holding the last spot, positive = chasing. Half-games are real.
- **`buildFormAndMovement`** rebuilds `last5` / `streak` ("W3") / `rankLastWeek` from the games table. ⚠️ Its cutoff is the **newest week holding a final game, read off the rows** — NOT `seasonManager.currentWeek`. The live board only reflects finals, so cutting at `currentWeek` includes every game already on screen and the movement column comes back **all zeroes** (it did); `currentWeek` is separately known-stale. `rankChange` compares **rank BY RECORD**, not display row — a rival winning its division reshuffles seeds around a club that never moved.
- Row fields: `division`, `divisionRecord`/`divisionWins`/`divisionLosses`, `leagueRecord`/`leagueWins`/`leagueLosses`, `seed`, `seedKind` (`division`|`wildcard`|null), `gamesBack`, `rankLastWeek`, `rankChange`, `streak` (string; the signed counter moved to `streakCount`), `last5`. League objects also carry `divisions: [{name, teamIds}]` in the owner's **config order** (`seasonManager._divisionNames`), so the four blocks don't reshuffle as results land. Regression: `test_standings_view.py`.

### League News Feed (`league_news.py`, `front_page.py`, `GET /api/front-page/news`)
**PERSISTED and cumulative.** An item is published the moment it happens, by whichever system it happened in, via `league_news.publish()`. It does **not** clear at the week rollover; it is fixed-length, and stories fall off because the reader asked for N of them.
- ⚠️ The first build GENERATED the feed from current state per request. That meant a clinch stopped being news the instant the standings moved past it, nothing from week 9 survived into week 10, and the feed reset weekly. Don't go back to that.
- ⚠️ Persisting at every `leagueHighlights.insert` site was considered and rejected — **89 call sites**, overwhelmingly play highlights rather than news.
- ⚠️ **The feed is CORES / META-SIMULATION centric** (owner, 2026-08-08) — the league told by the things running it, not a box score. Two changes carry that: individual big games no longer publish at all (`BIG_GAME_NEWS_ENABLED=False`), and the Cores now publish on a cadence rather than only at anomaly beats.
- ⚠️ **Hand-written items** (`POST /api/admin/league-news`, plus `GET`/`PATCH`/`DELETE`, all admin-gated; Admin page → **News** tab). Two kinds, chosen by `postAs`: a **league announcement** (category `announcement`, optional crest / league mark, optional `body` prose) or a post **AS A CORE** (category `cores`, so it renders in that Core's voice and colour and threads with the sim's own lines — borrowing just the icon looked right and read wrong). **`event_type='admin_post'`** is what tells a hand-written row from a system one; without it the management list would offer a delete button for the Cores' own chatter. **`pinned`** holds a row at the top: pinned rows are fetched **outside** the newest-~40 window (an unpinned notice is pushed out within a day of normal publishing), are reserved and uncapped in the row passes, and **outrank `NEVER_LEAD` and the lead age cutoff** — those rules stop the sim promoting the wrong thing automatically, and nothing pins itself. Ceiling `PINNED_MAX` (5). New columns `league_news_items.body` + `.pinned` (model + **inline migration**). The **league mark** rides in `core` as the sentinel `'league'` — decoded in `_announcementIcon` and `LeagueNews.tsx` only; a fourth icon source should get a real column.
- ⚠️ **`announcement` is the one HAND-WRITTEN category** (`POST /api/admin/league-news`, admin-gated). Everything else in the feed is published BY a system AT the moment its event happened; this has a human author, which is why it gets its own category rather than borrowing one — a reader can tell a written notice from a reported result, and the category is what exempts it downstream. **RESERVED and UNCAPPED** in `front_page`: taken in its own pass BEFORE meta and league rows (`ANNOUNCEMENT_CATEGORIES`), because a per-category cap that can drop it defeats the point of having posted it. Leads with no stat strip (`LEAD_WITHOUT_STATS`) at the top of `CATEGORY_PRIORITY`, default `leadWeight` 100 — above anything a game produces. Season/week are stamped from the sim, never accepted from the caller (the feed is ordered by publication time, and a wrong week misfiles the row against everything around it). Renders at the **noteworthy** weight in `LeagueNews.tsx`. Posted from the Admin page's **News** tab.
- ⚠️ **`_publishCriticalityNews` passed `lead_weight=` to `league_news.publish`, which takes `leadWeight=`** — a TypeError on every call, swallowed by the surrounding `except Exception`. Criticality and suppression therefore **never once reached the feed**: 17 seasons of the production database hold **zero** rows in that category. Fixed 2026-08-09. Any publisher wrapped in a bare except needs its kwargs checked against the signature, not assumed.
- **The Cores react BY NAME when a player awakens or is cleansed** (`coresManager.awakeningEntriesFor` → `_broadcastCoreEntries` from `anomalyManager`'s transition loop). ⚠️ **At most one exchange per weekly tick**, taking the most significant crossing — the per-player flavour line already fires for everyone, and an exchange each would bury a busy week under the Cores talking to themselves. ⚠️ These are **number-free**, which is what makes them publishable at all: the data-aware `observation` beats quote the raw aggregate and stay confined to the ephemeral `/api/cores/conversation`.
- **Publishers**: clinch / elimination (`seasonManager._publishTeamNews`); record broken and upset (`seasonManager._publishGameNews`, off both the regular-season and playoff completion paths); criticality threshold crossings (`anomalyManager._publishCriticalityNews`); rule changes (`ruleVoteManager`); anomaly transitions; **Cores lines** — `seasonManager._publishCoresWeekNews` at week end, a reaction to the slate every `CORES_GAME_NEWS_EVERY_WEEKS` (1) and untethered banter every `CORES_AMBIENT_NEWS_EVERY_WEEKS` (3), each turn of an exchange its own row sharing an `exchangeId`.
- ⚠️ **Nothing is an upset before `UPSET_MIN_WEEK` (8)** (owner, 2026-08-09). Every club's ELO **regresses halfway to 1500** at the season reset (`teamManager.updateEloRatings`), so the opening weeks of EVERY season — not just the league's first — price the whole league as average, and a `UPSET_NEWS_ELO_GAP` (120) gap there is as likely to be last season's residue as this season's form. A quarter of a 28-week season is where results outweigh the carried prior. Gates **both** surfaces: the feed's upset story (`_publishGameNewsInner`, on the 1-indexed season week) and the live **UPSET badge** (`floosball_game`, which also drives the game board's interest ranking). ⚠️ The badge check must special-case the **playoffs**: `seasonManager` stamps `gameType`/`playoffRound` on a playoff game and **never sets `.week`**, so a week-only test scores every postseason game as week 1 and kills the badge in the four weeks it matters most. Deliberately NOT gated: `SUPPORTER_UNDERDOG_WIN_BONUS` and the `house_money` card, which are economy payouts rather than editorial claims.
- ⚠️ **The Cores' `observation` beats never go in the feed.** They quote the raw aggregate and threshold; every public anomaly surface stays number-free so it reads as a mood rather than a progress bar. Those live only in the ephemeral `/api/cores/conversation`. Game-result reactions are fine — they reference teams and scores.
- ⚠️ **Nothing here may break a game.** `_publishGameNews` wraps its ENTIRE body, not just the inner checks: the first version read `self.currentWeek` (which lives on the **Season**, not the manager — the manager only grows one during the playoffs) above the inner try blocks, and the AttributeError raised straight out of `_simulateGame`, failing every game in the slate.
- **Record breaks** are detected by diffing a flattened snapshot of the records tree either side of `checkPlayerGameRecords`, NOT by instrumenting the dozens of `if stat > record` sites — a new record type can't silently skip the feed. Only a real break publishes (`previous > 0`), or a fresh league fires all ~60 records on its first game.
- **Big individual games are OFF** (`BIG_GAME_NEWS_ENABLED`, default False). Measured, they were **48% of all rows**, and since the display caps each category the visible feed was 100% box score. The machinery stays behind the flag rather than being deleted: `seasonManager.BIG_GAME_TESTS` records this sim's measured p50/p90/p99 over 9,401 player-game lines (NFL-shaped numbers put 3 sacks at 5.6% of every player-game), which is expensive to rederive and is the reference for any future "notable performance" surface. Re-measure if scoring moves.
- **Reading** (`front_page.buildLeagueNews`): newest first, no week or season filter.
- ⚠️ **The LEAD is the biggest story of the most recent MOMENT** — recency bucket (`LEAD_RECENCY_BUCKET_SECONDS`, 600, wide enough to hold a whole slate), then `lead_weight`, and category only as a last resort. **MEASURED over 790 rows**: ranking by a static category ladder inside the moment gave `upset` **88% of reader views on 24% of the eligible items** and buried `big_game` at 3% on 76%. A slate resolves in one instant, so the ladder was never a tiebreak — it was the sort.
- ⚠️ **`lead_weight` is "how far past its OWN bar", DIVIDED BY the median qualifying event of its category** (`seasonManager.LEAD_WEIGHT_REFERENCE`). The raw ratio is NOT comparable between categories — big-game thresholds are p99, `UPSET_NEWS_ELO_GAP` is far lower — and shipping it raw only moved upsets 88% → 78%. With the divisors: top category share **56% → 34%**. Re-measure if a threshold moves.
- **Records lead on THREE numbers** (old mark / new mark / gap) — requiring four locked every record out of the headline, and the lead strip already flexed to any cell count (`LEAD_MIN_STATS`).
- **`rules` and `criticality` lead with NO strip** (`LEAD_WITHOUT_STATS`, owner 2026-08-08) and carry weights above anything a game produces. For criticality a strip would be actively wrong, not merely absent. Cores lines never lead — they are voice, not report.
- **Rows: meta is RESERVED, not merely capped.** `META_CATEGORIES` (cores/criticality/rules/anomaly_transition) take up to `room // 2` in a first pass, the rest fill from `room // 3` per category, and the combined set is re-sorted back into publication order. A cap alone is only a ceiling: a playoff week fires a dozen clinches at once and fills the room before the Cores are reached (observed: 2 Cores rows out of 9). `NOTICE_CATEGORIES` (schedule) get **1** — "Week 12 begins" is a marker, not a story. The cap is **hard**; a first pass topped back up from the overflow, which undid it entirely.
- ⚠️ **A Cores exchange is ONE feed entry** (`front_page._groupExchanges`), its turns in SPOKEN order under a `turns` array, sitting where its newest turn sat. Without it the feed reads a conversation BACKWARDS — rows are newest-first and each turn is its own row published milliseconds apart, so the reply lands above the line it answers. It also counts as a **single row** against the caps, which is why `metaCap` is `room // 4` rather than `room // 2`.
- **No category label on a row** (owner, 2026-08-08) — the icon and a 2px colour rail carry the kind, the line carries the story. **Three weights of row**: `record`/`anomaly_transition`/`criticality`/`rules` render tinted and bolder (noteworthy); `schedule` renders as a small uppercase tinted BAND (a week starting is the line between stories, not one of them, and its tint is deliberately weaker than the noteworthy one); everything else is plain. A clinch is deliberately not highlighted — it happens sixteen times a season. A Core speaks with **their own icon and colour** (`item.core`/`coreDisplayName` ride on the payload); one flat Cores colour made a two-Core exchange read as one voice. Regression: `test_front_page_news.py`.
- `LeagueNewsItem` gained `team_id`, `stats_json` and `lead_weight` (model + **inline migration**).

### Offseason Flow (`seasonManager._handleOffseason`)
Phased, resumable (each phase gated by a completion marker in `simulation_state.offseason_completed_steps`). `_offseasonFlowPhase` values: `post_bowl → frontoffice → rookie_draft → pre_fa → fa_draft → training → None`.

Front-office decision steps (one `frontoffice_decisions` gate): **1** increment FA years → **2** resolve fire→hire coach votes (coach always backfilled) → **2.5** coach increments/retirements → **3** contract decrements + retirements → **3.5** resolve cut votes (release to FA pool) → **3.6** award "Scorched Earth" achievement. Then: rookie draft (live picks), FA draft (`_processFreeAgency`), training/HOF/finalize.
- **Position-supply floor** (`playerManager.ensurePositionSupply`, wrapper `seasonManager._ensurePositionSupply`): guarantees enough **draftable** players at EACH position to fill every roster slot (numTeams × {QB1,RB1,WR2,TE1,K1} + `ROSTER_SUPPLY_BUFFER_PER_POSITION`), generating only the per-position deficit into the FA pool. Supply counts **rostered + free agents only** — it **excludes `willRetire`** players AND **`is_prospect`** players (prospects/upcoming rookies are locked to their drafting team and can't fill another team's vacancy, so counting them overstated availability and let the FA pool come up short). Runs twice: at **week `GM_ACTIVE_WEEK`** and again **just before the FA draft** (catches FA retirements decided in the offseason). Idempotent (already-generated FAs count as supply).
- **FA draft never leaves a roster slot empty** (`playerManager.freeAgencyPickGenerator` / `conductFreeAgencySimulation`): three layers. (1) the supply floor above tops up draftable supply pre-draft; (2) the draft loop keys completion off `len(freeAgencyOrder)` (the collection iterated, not `len(teams)`) and **appends any team missing from the order** — the persisted playoff `faOrder` snapshot is taken before the two Floos Bowl finalists are appended, so on a resume it can be short and would otherwise spin to the 100-round safety valve and abandon open slots; (3) **last-resort generation** (`generateLastResortFreeAgent`) — if a team is on the clock with an open slot and `_attemptRosterFill` signs nothing (pool genuinely empty), generate a replacement FA into the draft's own working list and sign them. Validated over a 10-season prod-copy run: layer 1 alone keeps all 24 rosters full, last-resort stays dormant.

### Game Simulation (`floosball_game.py`)
- `playGame()` is the main loop — clock-based (900s/quarter, 600s OT). Pre-game it deep-copies attributes into `gameAttributes` and applies league compression, funding morale, fatigue, team disposition, and a mental soft-cap.
- Play-calling chain: `playCaller()` → (clock-management checks first) → `_computePlayWeights()` → `_getBasePlayWeights()` (down/distance table) → `_applySituationalMods()` → `_applyMatchupMods()` → `_applyCoachMods()` → `_applyGameplanMods()` → `_applyAwakenedMods()` → `_executeWeightedPlay()` → `_selectPassPlay()`. Separate `_fourthDownCaller()` and `_otPlayCaller()`.
- **Gameplan → play wiring**. What each gameplan field actually drives (master switch: `gameplan.WIRING_ENABLED`, default True — flip off to neutralize ALL gameplan influence for A/B tests):
  - **Offensive** (`Game._applyGameplanMods`, in the play-weight chain): `runPassRatio` (run/pass balance — nudges the `run` weight up / four pass tiers down, consts `RUNPASS_RUN_SWING`/`RUNPASS_PASS_SWING`) and `passDepthBias` (quick vs deep passing — biases short/med/long/deep). Both were previously unconsumed; now wired here. `gapDistribution` drives run-gap selection (`runPlay`, ~`:9655`). `passDepthDistribution` was dead and is **retired**. `_runPassBias()` is dead code (never called). Play *depth* mods run before the awakened / FG-drain layers so a powered feed or clock-drain still overrides.
  - `passDepthBias` is set by `adjustOffensiveGameplan` (gameplan.py) when the offense is STALLING (both run+pass below average), scaled by **`offensiveMind`** (a sharp coach dials into a quick, high-percentage passing game; a poor one flails). **Situational**: `_applyGameplanMods` suppresses it in catch-up mode (behind 2+ scores in the 2nd half, or any deficit late — consts `QUICKGAME_SUPPRESS_DEFICIT`/`QUICKGAME_LATE_DEFICIT`) so the deep/desperation calling rides when chunk plays are needed.
  - **Defensive** — all live via `gameplan.getDefensiveScheme()`, called every play in `runPlay`/`passPlay` (its `runDefMult`/`passDefMult`/`passRushMult`/`coverageType`/`blitzPackage` outputs feed the run/pass outcome resolution): `blitzFrequency` (per-play blitz roll), `runStopFocus` (zero-sum run-D vs pass-D tilt), `coverageTendency` (man/zone/match choice via `_pickCoverage`), `coverageAssignments` (who blitzes, `_captureBlitzer` ~`:9200`). These have been wired all along (they are NOT display-only — the serialized copies in play-insights are just a mirror).
- **Awakened play-calling bias** (`_applyAwakenedMods` + the openness nudge in `selectPassTarget`): the offense **feeds a powered-up (awakened) skill player** instead of ignoring their state. An awakened **RB** multiplies the `run` weight (`AWAKENED_PLAYCALL_RUN_BIAS` 2.2); an awakened **WR/TE** multiplies the pass tiers (`AWAKENED_PLAYCALL_PASS_BIAS` 1.7) AND gets a perceived-openness bump so the QB looks their way (`AWAKENED_RECEIVER_OPENNESS_BONUS` 22). QB/K need no play-type bias (QB touches every pass; a charged K is handled by the FG-range logic). Keys off `_awakenedCharge` membership (awakened THIS game), so it's a no-op when the awakened system is off. Multiplicative under the situational/clock layers, so desperation passing still overrides a run bias. Fixes a powered-up RB sitting through 6 straight passes.
- **QB sneaks** (`_isSneakSituation`/`_selectRunConcept`, resolved inside `runPlay`): the QB follows the interior surge for the yard. A **run concept** (`RUN_CONCEPTS['sneak']`) with `base: 0.0` — it is *never* in the normal weighting; `_selectRunConcept` skips it and injects its weight only when the situation qualifies, so it can't leak onto 1st-and-10. **Two ways in**: 3rd/4th-and-≤`QB_SNEAK_MAX_YTG`, or inside `QB_SNEAK_GOAL_LINE_YTE` of the goal on ANY down. Suppressed in hurry-up (a sneak burns clock and stays in bounds). The QB is the runner via `_forcedRunner` — the same hook the reverse uses for a WR. **It does NOT run the three-gate model**: a sneak has a high floor and no ceiling, so it resolves on one push (`QB_SNEAK_BASE_SUCCESS` ± the QB's power/discipline vs effective run D) and rejoins the shared run tail (awakened fire, stretch, fumble, crediting). Gates 2/3 would occasionally spring a 40-yard QB run out of a goal-line pile. Punished harder by a stacked box than power is (`edge.runFocus` -0.55), helped slightly by a blitz. PBP keys off `play.sneakConverted` (whether the surge got there), not yardage. Measured in a fast sim: ~1.25 QB carries/game league-wide, QB longest-run p50=2 / p90=3 (the 20+ tail is scrambles, unchanged). Regression: `test_qb_sneak.py`.
- **Ball-carrier moves** (`_runnerMove`, applied in the shared carrier tail used by BOTH runs and receptions, immediately before `_stretchForFirst`): stiff arm / spin / hurdle. Follows a three-part model now shared by every audacious play in the sim — **willingness** from `_flair` (creativity + xFactor, 0-1, 0.5 at the house-neutral 80) plus mental state (`_confidenceState` + the new `_determinationState`); **ability** from the move's own physical attribute (`RUNNER_MOVES`: stiff arm→power, spin→agility, hurdle→agility/speed), picked to fit the carrier's build; **risk** from `_undiscipline` (a fumble bump taken on for ATTEMPTING it, made or missed). Flair deliberately never touches whether a move WORKS — that would make it a generic yardage buff. **This is why the feature exists:** `xFactor` and `creativity` were nearly inert in resolution (xFactor in one QB-mobility calc, creativity in two concept exec weights). The same terms were retro-fitted to the two pre-existing audacious plays — `_stretchForFirst` (`STRETCH_FLAIR_K`/`STRETCH_DETERMINATION_K`) and the diving catch (`DIVE_FLAIR_K`/`DIVE_DETERMINATION_K`). **Gated to the point of contact** (`RUNNER_MOVE_MAX_CONTACT_YARDS` 12) — past that the carrier is in open field with nobody to beat. **The defender resists with SKILL *and* DISCIPLINE**: `defRating` blends `tackling` (0.6) with `discipline` (0.4), and discipline additionally resists in proportion to the move's own `risk` (`RUNNER_MOVE_DISCIPLINE_RISK_K`) — so a squared-up veteran takes a hurdle away hardest, which is what nullifying flair should mean. ⚠️ The primary tackler is now resolved BEFORE the move (it used to be identified below the fumble check, so `_runnerMove` was handed `None` on BOTH paths and no individual defender ever resisted). On success: yards, a PBP clause, and a small two-sided confidence swing — there is **no missed-tackle stat** in `stat_tracker` to credit, and adding one is a schema change. **Footprint measured directly rather than from sim scoring**: +0.119 yards per carry (14% attempt rate at contact, 47% success). Paired fresh sims could NOT resolve this — their run-to-run spread (27.4-31.1 pts/g across four runs) swamps a tenth of a yard, so earlier scoring deltas attributed to this feature were population noise. Flag `RUNNER_MOVE_ENABLED`. Regression: `test_runner_moves.py`.
- **Pre-snap recognition** (`_applyPreSnapRead`/`_preSnapLeverage`, called at scheme time in BOTH `runPlay` and `passPlay` so every path — RPO, sneak-look, tricks — is covered): the defense **commits to run or pass before the play resolves** and is right or wrong. This is the mirror of the RPO read, and it fills a real hole: every other deception in the sim is an OFFENSIVE execution roll against the defense's *standing gameplan numbers* (`conceptTelegraphed` is the runner executing badly; play-action bites per a pre-set `runStopFocus`; tricks pay off against a tendency), so the defense never made a per-play decision — and `defensiveMind` did **no per-play work at all**, appearing only in insight payloads. Accuracy = `PRESNAP_READ_BASE` (0.50) + skill from the D-coach's `defensiveMind` (60%) and the on-field readers' `instinct`/`focus` (40%, the LB/S = their RB/QB), minus a **disguise** penalty per fake (`PRESNAP_DISGUISE`: rpo .30 / trick .32 / sneakLook .28 / playAction .22) — the first time a fake beats a *decision* rather than a standing tendency. **Run concepts disguise too, but only `draw`** (`PRESNAP_CONCEPT_DISGUISE`, .24, scaled by how well that back sells it via `_runConceptExecQ`): a draw is a run that looks like a pass, i.e. play-action pointed the other way, so it attacks exactly the question this layer asks. `counter`/`sweep` are deliberately excluded — they deceive about DIRECTION, which a run/pass commit can't be fooled about; they already collect in the concept-edge channel, and they'd earn a disguise only if the layer grew a directional commit. Measured: draw is 12.0% of run calls, worth -0.210 accuracy, moving the run-side league read 0.5173 → 0.4922 (just under a coin flip) and pulling the layer's overall bias from +3.47% to ≈+1.2% of the edge swing. **Zero-sum by construction**: correct multiplies the matching multiplier by `(1 + swing)`, wrong by `(1 - swing)`, so a league-average defense nets nothing. Measured across 24 real defenses, mean accuracy **0.5173** → expected multiplier 1.0016, i.e. **0.16% stronger defense league-wide** (spread 0.374–0.653, so sharp defenses genuinely gain). Scaled by `_preSnapLeverage` — the floor applies at obvious distances (ytg ≤2 or ≥12), which is both realistic and what stops it double-counting with `getDefensiveScheme`'s situational branch. Flag `PRESNAP_READ_ENABLED`. Regression: `test_presnap_read.py`.
- **Defensive response to the sneak** — three layers, no formation/pre-snap layer exists in the sim: (1) **situational** — `getDefensiveScheme` stacks the box whenever `yardsToGo <= 3`, and *more* on late downs (`×1.35` on 3rd/4th). This branch previously read `down in (1, 2)`, so 3rd- and 4th-and-short matched **no branch at all** and the defense played neutral on 4th-and-1; (2) **adaptive** — `adjustDefensiveGameplan` folds `sneak` into the box-stacking term at 1.3× the weight of `power` (sneak wasn't in the counter terms at all before, so a team could sneak every short down unopposed); (3) **matchup** — the concept's own `edge.runFocus -0.55` punishes it against a run-committed plan. Measured effect of (1)+(2) over ~1,700-game sims: QB ypc **2.01 → 1.55** with league scoring (27.4 → 27.7) and RB ypc (4.04 → 4.04) unmoved, i.e. the counterplay lands on sneaks specifically.
- **Sneak-look trick** (`_selectSneakLook`/`_executeSneakLook`): show the sneak, then pitch outside to the RB or throw quick into the vacated flat. Gated like the other trick plays — bold coaches only, and only when the D has actually committed (`runStopFocus` ≥ `SNEAK_LOOK_MIN_RUNFOCUS`), never on 4th down. The pitch reuses the `sweep` concept + `_trickRunRelief`; the throw reuses the RPO openness channel. Tunables `SNEAK_LOOK_*`.
- **Clock management** triggers (all checked at top of `playCaller` when `down ≤ 3`): kneel (Q4/OT, leading, deterministic drain math), spike (Q2/Q4/OT, no timeouts, ≤120s, trailing/tied), offensive timeout (trailing/tied, has timeouts).
- **Score LAST, not fast** — two drain modes, one per scoring type. `_isFgDrainMode` (long-standing) covers a deficit of **0-3**: bleed the clock, then kick with ~7s left. `_isTdDrainMode` (new) covers **4-8**, the band a touchdown erases — an offense inside `TD_DRAIN_MAX_YARDS` (5) on 1st/2nd down with 25-90s left holds the score instead of racing. Measured before it existed: 1st-and-goal from the 3, down 5 with 0:55, the offense took a 12-second huddle, scored immediately and handed back ~45s plus timeouts for a winning FG. Both suppress sideline targeting (an out-of-bounds catch stops the clock) and bias toward in-bounds runs — the TD version more mildly (run ×2.0 vs ×3.0), because a kick ends it from where it stands but a touchdown still has to cross the line. Down 9+ is excluded: two scores needed, so the clock is the enemy and hurrying is right. Down 7/8 are INCLUDED even though a TD only ties, because a tie means overtime and leftover time lets the opponent win in regulation. ⚠️ There is deliberately **no goal-to-go test** — 2nd-and-1 from the 3 is not goal-to-go and is exactly as good a place to hold from, so proximity + spare downs is the condition. Regression: `test_td_drain.py`.
- **Defensive timeouts** (`Game._checkDefensiveTimeout`, post-play): a trailing defense burns timeouts to get the ball back (Q4/OT inside 2:00, or 3:00 when down multiple scores; Q2 inside 0:60 regardless of score). ⚠️ **A LEADING or TIED defense also stops the clock when its lead is about to evaporate** (`_leadIsAboutToEvaporate`), on **two limbs, one per scoring type**: a KICK erases a lead ≤ `_fgValue()` from anywhere in the offense's range; a TOUCHDOWN erases up to `_maxPossession()` but only from inside `LEAD_THREAT_TD_YARDS` (10). The second limb closes a hole the width of the red zone — up 5 with the opponent on your 3, a FG does not help them so the kick limb calls the clock your friend, but they are scoring a TD to go ahead. It is the direct counterpart to `_isTdDrainMode`: the defense's window (10 yards) deliberately CONTAINS the offense's (5), so there is no band where the offense can bleed the clock and the defense is not allowed to stop it. Draining only helps the leader while the lead SURVIVES the drive — once a kick ties or wins it, every second run off comes out of the leader's OWN answer. Observed live: a defense up 3 let the offense milk from inside FG range and kick with 0:07 left while holding three timeouts. Bounded at 3 deliberately — at 4+ a FG leaves the leader ahead, so the clock genuinely is their friend. Range is read from the offense's kicker (`maxFgDistance`, including a charged awakened kicker), not a constant. Regression: `test_leading_defense_timeout.py`.
- **QB scrambles** (`_qbEscapesSack`/`_qbTucksAndRuns`/`_resolveQbScramble`, inside `passPlay()`): a mobile QB runs instead of taking a sack or throwing it away. **Agility gates** whether they scramble; **speed drives** the yardage (small agility bonus). Two trigger paths: (1) the sack branch (an agile QB escapes a would-be sack) and (2) the **throwaway branch** (no one open → tuck and run, **the primary path** since sacks are only ~0.8/game). A scramble flips `playType=Run` + `runner=passer` and reuses the run-crediting tail (carries/rush yards/TDs/longest/20+, defense run yards, a tackler credit, small fumble chance) so clock/WPA/box-score/fantasy all flow through the existing run paths. It does **not** call `runPlay()`, is **not** a sack (no sack stats), and is **not** a pass attempt (the throwaway path un-charges the attempt booked at the top of the branch via `stat_tracker.remove_pass_attempt`). `mustThrow` (desperation 4th-down/late) suppresses the tuck-and-run. PBP narrated as a scramble (`floosball_game.py:3380`, gender-neutral), with phrasing split by `play.scrambleReason` — `pressure` (escaped a sack) vs `coverage` (no one open, tucked it). Tunables in `constants.py` (`QB_SCRAMBLE_*`); flip `QB_SCRAMBLE_ENABLED=False` to disable. Volume in fast sims ≈ top mobile QB ~12 carries/season (~0.5/game), ~10 QBs scramble per season, ypc ~5. Plan: `docs/QB_SCRAMBLES_PLAN.md`.
- **Team form oscillation** (`seasonManager._updateTeamFormOffsets` weekly -> `Game._applyFormOffset` pre-game): a continuous per-team `formOffset` (±`FORM_MAX`, a multiplier on `gameAttributes`) so clubs run hot and cold ACROSS a season instead of playing at one fixed level all year. Baseline before it existed: sd of a club's wins across the four game days 1.06 vs a coin-flip line of 1.32 (form varied LESS than chance), and corr(day-1 wins, final wins) +0.750 — the season was legible from game one. **`FORM_FEEDBACK='momentum'`**: a run feeds itself and a slump deepens, bounded by an unconditional weekly `FORM_DECAY` rather than by a restoring force. The originally-specced mean-reverting mode is kept as `'reverting'` for A/B but is **not recommended** — it moved form variance only 1.06 -> 1.11, and the failure is structural rather than a tuning miss: an arc IS a sustained multi-week deviation and negative feedback exists to cancel exactly that. **Confirmed at 96 seasons/arm (8 leagues x 12, ~3,060 team-seasons):** form variance 1.03 -> 1.44 (past the 1.32 chance line), flat clubs 48% -> 20%, corr(day-1, final) +0.784 -> +0.504 (r2 0.61 -> 0.25). The variance is genuinely arc-shaped, not jitter: turnarounds (bottom half after day 1 -> top quarter) 2.1% -> 6.0% and collapses 2.3% -> 6.4% both roughly TRIPLE and move symmetrically, with longer runs both ways (win streak 5.25 -> 6.05, losing streak 5.09 -> 6.07). Direction is trait-scaled — `team.collectiveResolve()` (mean `adversityResolve`) rides a run, `collectiveVulnerability()` (mean `complacencyVulnerability`) deepens a collapse. **Carries into the playoffs** at `FORM_PLAYOFF_SCALE` (0.5) — the offset stops UPDATING at season end, but removing it at kickoff measurably made the bracket more predictable (a club that surged late lost its surge exactly when it mattered); full weight is too loose (top seed wins only 8%). Persisted to `teams.form_offset` **by the layer itself** (`teamManager.saveTeamData()` only runs at app init); reset to 0 at season start. Separate from `FORM_STATE_RATING_MULT`, which stays the discrete badge layer. Harness `form_oscillation_check.py`; full measured curve in `constants.py` + `docs/DIVISIONS_PLAN.md`.
- **Pass pressure + depth** (`SACK_BASE_RATE`, `SACK_PROB_CAP`, `RB_CHECKDOWN_PRESSURE_CHANCE`, `PASS_DEPTH_MEANS`). Sacks were **0.33 per team per game against a real-world ~2.4** — two multiplicative suppressors: the base rate at an even matchup was half of reality, and **45% of would-be sacks were dumped to the RB** before a sack could register (`rbDumps`, ahead of the sack branch). A rush that never gets home also inflates completion % and attempts, so it distorted the whole passing picture, not just the sack column. Separately the air-yard bands were compressed — "medium" at 6.5 air yards is really a short throw — holding league aDOT at 6.29 vs ~7.8 and making every completion tiny (Y/C 7.24 vs ~11.2). ⚠️ **`SACK_BASE_RATE` is a CURVE parameter, not the realized rate**: protection systematically outweighs the rush (`qbProtection = qbMobility + blockingModifier*4`), so the typical `rushDifferential` is negative and the logistic lands well below it. 14.0 yields ~6.0% of dropbacks = 2.48 sacks/team/game. Measured pre-session → shipped (3 leagues x 3 seasons/arm): **sacks 0.26 → 2.53, pass yards 213.0 → 240.6, aDOT 5.84 → 7.57, Y/C 7.41 → 8.43, Y/A 5.09 → 5.90, pass TD 0.84 → 1.11, scoring 31.4 → 37.4** (which is the documented ~36 target — the sim was BELOW it before). ✅ **Interceptions never moved: 0.33 → 0.33** across every arm, including the deepest. Deeper passing did not inflate turnovers, which was the explicit guardrail. **YAC tier caps** (`YAC_TIER_CAPS`): the ceilings were nearly FLAT across pass tiers — a short pass had almost the same explosive ceiling as a deep one (housecall mean 12 vs 14) — so most big pass plays were short throws with a long run after, and a called "long" play could travel ~10 yards through the air and still be the smaller gain. Short/medium ceilings are now tightened and the long/deep air bands lengthened, which **redistributes** yardage toward genuine downfield throws instead of adding any. ⚠️ **Raising YAC globally does NOT work**: measured arms lifting `YAC_GATE_A_BASE`/`_CAP` ran pass yards to 262-282 and scoring to 43-47. The arithmetic is the reason — at 41 attempts, reaching NFL's 11.2 Y/C while holding ~235 yards needs completion% near 52%. The sim throws 41 times vs NFL's ~35, and that extra volume is *why* everything has to be short. `FIRST_DOWN_RUN_WEIGHT` was tried as the offset and barely moved attempts (40.8 → 39.5 at weight 64), because more runs sustain drives and raise total plays. **Still open**: Y/C 8.43 vs ~11.2 and YAC 31% vs ~50%. Closing it requires cutting pass VOLUME (attempts 41 → ~35, i.e. plays/team/game 68.5 → ~63), which is a clock/drive-length question, not a passing-model one.
- **Punts** (`Game.resolvePunt`, `PUNT_*` constants). Was one line — `randint(70*legStrength/100 - 20, ...)` — with no accuracy, no placement, no touchback risk, and no reason to punt differently from your own 5 than from midfield. Leg strength IS the right lever for a punt (unlike a field goal, where it only sets range), but distance alone is not the job. Four types chosen by field position: **boomer** (own end, pure leg, flip the field), **standard**, **pin** (near midfield — shorter and higher, aim to down it inside the 20), **coffin** (the audacious one — sideline inside the 10; a miss is a touchback that gives the placement back). Ability is ACCURACY; willingness to try the coffin corner comes from `flairOf()` (creativity + xFactor) — the same three-part model as runner moves and diving catches. `flairOf` is now module-level so `Game` (punt selection) and `Play` (runner moves, diving catches) share ONE implementation. ⚠️ **The inside-20 rate is GEOMETRIC, not placement-driven** — halving the placement success rates moved it 52% → 53%, because a 46-yard punt from your own 35 lands inside the 20 however it was struck. What was actually missing was the **return game**.
- **Punt returns** (`Game._resolvePuntReturn`, `Game._pickReturner`, `PUNT_RETURN_*` / `PUNT_FAIRCATCH_*` / `PUNT_MUFF_*`). Returner is the most explosive of WR1/WR2/RB by speed+agility, not a fixed slot. **Fair catch is a DECISION** (depth vs coverage closing, read quality from `instinct`), not a distance rule. A **pin or coffin punt hangs**, so it raises both the fair-catch rate and the muff rate — that is the trade the punter makes when he gives up distance for placement. **Muffs** are modelled (hands/focus prevent, hang causes; `PUNT_MUFF_RECOVER_KICKING` decides who comes up with it) and a kicking-team recovery is the biggest swing on a punt. **Return touchdowns are possible** — the field ahead is `100 - landing`, and the first implementation capped returns below that, making a punt-return TD structurally impossible. Returner production is credited to the RETURNER in a new `returning` stat group (`puntReturns`, `puntReturnYards`, `puntReturnTds`, `fairCatches`, `muffs`, `longest`) persisted in a new `returning_stats` JSON column on the three player stat tables (model + inline migration + load/save plumbing). ⚠️ **Coordinate trap**: `landing` is yards from the RECEIVING team's OWN goal, so a return INCREASES it. Subtracting drove the ball backwards and pushed inside-20 to 62% — impossible if returns work, which is what surfaced the bug. Measured: gross 46.2 (NFL ~46), **net 40.8 (~41)**, inside-20 39% (~35%), yards/return 8.9 (~9), return TDs 3.0 per 100 games (~4), longest 89 (~90), fair-catch 36% (~40%), muff 2.3% (~2%). Touchbacks run 1% vs ~5% — the one number still light. Kicker stats: `punts`, `puntYards` (gross), `puntReturnYards`, `puntsInside20`, `puntsInside10`, `puntTouchbacks`, `puntLongest` — `puntLongest` is a MAX so it is written across the three stat dicts directly rather than through `add_stat`, which only sums.
- **Punt execution has degrees of success.** Originally only the coffin corner had any downside — a failed PIN silently landed at its distance draw (i.e. still a good punt), and boomer/standard had no execution model at all, so a routine punt could never cost a team field position. Now: a **shank** (`PUNT_SHANK_*`, ~4% base, accuracy-driven, applies to EVERY type and cancels whatever placement was intended); a missed **pin** either sails too deep for a touchback (`PUNT_PIN_TOODEEP`) or comes up short into returnable territory (`PUNT_PIN_SHORT_*`); the coffin corner keeps its three-way hit / touchback / missed-but-recoverable split. Accuracy now separates punters sharply — pin→inside-20 runs 16.5% for an elite punter vs 4.0% for a poor-accuracy one, and shanks go from ~6% to nil across that range. ⚠️ These are correct behaviour but they cost ~2.5 yards of league gross average, so `PUNT_MAX_YARDS_PER_LEG` was raised 0.70 → 0.755 to absorb them — tune the two together. Measured: gross 46.9 (NFL ~46), net 41.5 (~41), inside-20 37% (~35%), touchbacks 5% (~5%), yards/return 9.4 (~9), longest 74 (~70).
- **Punt clock** (`PUNT_HANG_SECONDS`, `PUNT_RETURN_SECS_PER_YARD`): a punt burned only 4-6s (snap to kick), but the ball hangs and the return takes time, so the live-ball portion is far longer. Duration is now kick + hang + return time. ⚠️ The clock still **stops after every punt** regardless of whether the returner was tackled in bounds — a punt is a change of possession (owner correction 2026-08-05; an earlier version of this kept the clock running on an in-bounds return, which is wrong).
- **Punt play-by-play** (`Game._puntPlayText`, split out of `formatPlayText`): every punt used to read "X punts" and stop, so a fair catch, a touchback, a 40-yard return and a shank were indistinguishable. Now names the returner and the yards, the touchback, the muff and who recovered it, the shank, and the return touchdown. Phrasing rule worth keeping: a ball landing inside the 10 reads **"downed at the N"** rather than a fair catch, since no returner is standing under that ball. There is deliberately **no "pinned at the N" suffix** — it was tried and cut as noise (owner call 2026-08-05). Regression: `test_punt_play_text.py`.
- **Punt telemetry for the field graphic**: `puntType`, `puntAction` (fairCatch|return|muff|touchdown), `puntLanding`, `puntGross`, `puntTouchback`, `returnYards`, `returnerName` ride on the `game_state` lastPlay payload and the per-play list. `yardsGained` on a punt is the GROSS kick, so the arc draws to `puntLanding` and the return is a SEPARATE leg back from it.
- **Field goals** (`Game.fgMakeProbability` — THE single source of truth, shared by the coach's attempt decision, the kick resolution, the PAT estimate and the OT win-probability model; those were four separate copies of the curve that could and did drift). **Leg strength does NOT decide success** — it sets RANGE via `maxFgDistance`, and enters only through the MARGIN (how much leg is to spare at this distance). `FG_ACCURACY_WEIGHT` is the primary skill term, `FG_MARGIN_WEIGHT` scales the spare-leg term, and the existing pressure layer (pressureHandling + focus/discipline) handles nerve. Previously success keyed off the kicker's OVERALL rating, making leg ~30% of the outcome and **playmaking + xFactor 40%**, neither of which should decide whether a kick is on line. Curve recentred: `FG_CURVE_CENTER` 58 / `FG_CURVE_SLOPE` 0.14 (was centre 52 / slope 0.18, which put an average kicker at ~50% from 52 yards where real kickers are ~68%). Measured league FG% ≈ 80% (NFL ~84%). Resulting shape — an average kicker (80 leg / 80 acc) makes ~69% from 52 and is range-capped at 58; a big-leg/poor-accuracy kicker (96/70) reaches 64 yards but converts only ~59% from 52; only elite-both (96/94) clears 60+ at a useful rate. ⚠️ **`fgMinAttemptProb` was 0.20**, which sent kickers out on attempts a punt beats comfortably (a miss hands the opponent the ball at the spot instead of pinning them). **That was the kicker anomaly**: more leg meant more marginal long tries, so a BETTER kicker measured as WORSE for his team. Raised to 0.38. Re-measured with `FLOOS_POS_FORCE`: kicker impact **−0.93 → +0.87 wins**, and the positional table is now QB +1.70, RB +1.46, WR +1.06, K +0.87, TE +0.71.
- **Yardage draws use `_rnd()`, never `int()`** (`floosball_game._rnd`): `int()` truncates TOWARD ZERO, which collapsed every random draw in the open interval (-1, 1) to exactly 0 and shaved ~0.5 off every positive draw. Two artefacts across the whole sim: an artificial spike of zero-yard plays — P(<=0) on a lost line contact measured **47% against the 20% the distribution actually implies**, driving an RB stuff rate of 28-31% vs a real-world ~18% — and every configured mean behaving ~0.5 lower than it read. It was long-standing (the pre-gate-model cascade had it too). All 22 random yardage draws now use `_rnd` (unbiased, `floor(x + 0.5)`), and **the means were retuned downward at the same time** because they had been implicitly calibrated around the truncation. ⚠️ Anyone adding a yardage draw must use `_rnd`, not `int` — `int()` will silently reintroduce both the zero spike and the downward bias. Measured before → after: **stuff rate 28.5% → 21.0%, 20+ runs/game 2.41 → 1.97, ypc 4.58 → 4.48, rush yards 121.6 → 118.5**, with pass yards 229.9 → 236.1 and scoring 36.7 → 37.6. Note the `aDOT` stat records the INTENDED tier depth (`PASS_DEPTH_MEANS`), not the realised draw, so it cannot be used to detect this class of bias.
- **Run gate model** (`Game._resolveRunGates`, `RUN_GATE_MODEL_V2`, `FLOOS_RUN_GATES=off` to revert): a carry is three contests — the line, the second level, the open field — and the runner's **momentum state carries between them**, which is what makes the stages mean anything. `clean` (untouched, full speed) gets an edge at the next gate; `contacted` (broke a tackle, legs gone) is roughly even; `fought` (squeezed through a plugged gap) is at a disadvantage (`RUN_STATE_EDGE`). Gate 1 is tiered by gap quality: at/above `RUN_GAP_OPEN` the carrier releases untouched with no tackle attempt; between that and `RUN_GAP_PLUGGED` a defender is in the hole for an even contest; below it the defender has the edge and only an elite back busts out. At each contact the carrier either **powers through** (power + discipline) or **elects a move** — `_flair()` (creativity + xFactor) decides whether he tries something, the move's own attribute decides whether it works. Gate 2 is rarely uncontested; a blitzing LB is out of the run fit and gives an edge (`RUN_BLITZ_EDGE`), **not** a free pass. Gate 3 is a pure speed contest for a still-clean carrier (no move saves you from a correct angle) and a speed/agility contest with moves otherwise. Each stage draws a real named defender via the position mapping (`_levelDefender`: TE→DE / RB→LB / QB→S). ⚠️ **`brokenTackles` counts DOWNFIELD breaks only** — winning the contact at the line is getting through the front, not breaking a tackle, and counting it as one read several times too high; line wins are tracked separately as `lineWins` in the gate outcome. **Calibration is delicate**: the first build ran league ypc to 9.61 and 61 pts/game because a broken tackle paid the full break-through reward and a blitz skipped the stage entirely. Seven tuning passes to land it. Where it sits vs the flat cascade: **ypc 4.61 vs 4.22 (+9%), 20+ runs +16%, stuff rate 28.5% vs 31.4%, scoring 33.4 vs 33.0 (matched), longest 93 vs 96.** Still slightly hot on ypc; the levers are `RUN_BREAK_BASE`, `RUN_STATE_EDGE` and the per-stage yardage bands. This also fixes `yardsAfterContact`, which is now a real stat (**80% of rush yards**, from 4% when it only captured a post-hoc move bonus) because contact is resolved inside the cascade at a known point rather than assumed after the fact.
- **Advanced metrics** (`stats_optimization.py` dataclasses -> `to_legacy_dict()` -> the game/season/career JSON blobs). **No migration needed** — `GamePlayerStats`, `PlayerSeasonStats` and `PlayerCareerStats` all keep JSON blobs alongside their denormalized columns, so new keys ride along. ⚠️ The live stat dicts come from `OptimizedPlayerStats.to_legacy_dict()`, **NOT** from `floosball_player.playerStatsDict` — that template is only the canonical key set used by `mergeStatDefaults()`. A new metric must be added to the dataclass (field + `reset()` + `copy_from()`) AND emitted in `to_legacy_dict()`, or it silently never appears; `StatTracker.add_stat` skips unknown keys without erroring. `mergeStatDefaults()` runs on the season + career load paths so players whose stored blobs predate a metric still accumulate it. Record via `Player.addAdvanced(StatCategory, key, amount)`.
  - **QB**: `sacked` (sacks taken — the defense recorded them, the QB never did), `throws`, `throwQualitySum`, `badThrows` (below `BAD_THROW_THRESHOLD`), `airYardsSum` (banked at RELEASE, using per-`PassType` means, so aDOT covers incompletions).
  - **RB**: `yardsAfterContact` (now a real stat at ~80% of rush yards — the run gate model resolves contact at a known point; it was 4% when it only captured a post-hoc move bonus), `brokenTackles` / `moveAttempts` / `tackleAttempts` (a failed gate IS a tackle attempt — the signal the flat cascade never surfaced; ~1.44 attempts per carry, breaks are downfield-only so the rate is low by design), `stuffs`, `gapQualitySum` (avg blocking faced, separating the back from his line).
  - **WR/TE**: `contestedTargets` / `contestedCatches` (openness below `CONTESTED_OPENNESS_THRESHOLD` at release), `bailouts` (caught a ball below `BAD_THROW_THRESHOLD` — credits the receiver for rescuing a bad throw).
  - Baselines from a fresh season: avg throw quality 66.6, bad-throw rate 7.6%, aDOT 6.2, contested-catch rate 63%, RB stuff rate 29.6%, avg gap quality 53.9.
- **WPA drop attribution** (`WPA_DROP_RECEIVER_SHARE` 0.7): a dropped pass charges the RECEIVER, not the passer. Previously every non-completion — including drops — put 100% of the negative swing on the QB while completions gave them only `WPA_PASS_QB_SHARE` (60%) of the upside, so quarterbacks structurally ate every bad pass outcome and took a share of every good one. That fed the MVP ballot via `MVP_WPA_WEIGHT`. The QB keeps 30% because drop probability scales with how poorly the ball was placed.
- **Positional impact is measurable** via `FLOOS_POS_FORCE` / `FLOOS_POS_SLOT` (`Game._applyPositionForce`): boosts one roster slot on even-id teams and cuts it on odd-id ones, so the win-rate gap gives a position's CAUSAL impact on winning, immune to how well its rating summarises it. Measured at ±12%, wins per season: **QB +2.52, RB +1.25, WR +0.91, TE +0.54, K −0.93**. So QB is by far the most impactful position — roughly double an RB — even though `corr(QB rating, wins)` is the LOWEST of the offensive positions (+0.253 vs WR's +0.451). The rating, not the position, is what under-describes quarterbacks. (A better kicker used to make the team WORSE at −0.93 wins; that was `fgMinAttemptProb` at 0.20 sending kickers out on marginal long attempts. Fixed — see the field-goal entry above.)
- **Leading teams ease off** (`Game.leadEaseOffFactor`, `LEAD_EASE_OFF_ENABLED` / `LEAD_EASE_OFF_MAX` 0.15): scales the LEADING team's effective run D, pass D and pass rush DOWN in the second half when they are up more than two scores, ramping with lead size and quarter. The sim modelled the trailing team giving up (`_isGarbageTime` stops them hurrying/spiking) but never the leader easing off, so a club building a blowout pressed at full intensity for four quarters and the trailing side often finished with nothing. Real teams rush three and keep everything in front once the result is settled — that soft coverage is why a blowout still usually has the loser scoring once. Paired with a **Q3 blowout drain** (the lead-protection floor in `_applySituationalMods` was Q4-only, so a rout built in Q3 kept getting aired out; a 3+ score Q3 lead now leans run and suppresses deep/long). **DEFENSE-only** — the leading offense is affected separately and only through play-CALLING, its execution untouched. **Coach-scaled**: `0.5*(1-aggressiveness) + 0.5*clockManagement` maps to a 0.4x (killer keeps his foot down, defense stays at 94%) .. 1.6x (professional calls off the dogs, 76%) multiplier, centred at 1.0 for a neutral coach. The Q3 drain is coach-scaled too (`_mul`); the Q4 floor stays flat because nobody should be firing deep on a Q4 lead. Together these took the form layer's shutout side-effect from +2.5pp to **below control** (7.6% -> 7.1% of team-games, <=3-point rate 16.7% -> 16.3%) while every arc and parity gain survived. `FORM_DOWNSIDE_SCALE` (0.6) is a third, smaller knob damping only the negative half of the form offset — arcs come from the swing, not the depth of the trough.
- **Rating-multiplier -> win-probability transfer = 1.619** (i.e. a ±10% roster-wide multiplier is worth **±4.5 wins per 28-game season**). Measured over 16,128 team-games via `FLOOS_FORM_FORCE`, which pins half the league at +X and half at -X for whole seasons and reads off the win-rate gap (`Game._applyFormOffset`). **Measure this before tuning any pre-game rating layer** — the transfer is far steeper than it looks, and a layer that seems weak is usually one whose value never sits near its clamp, not one whose lever is small.
- **Pre-game modifiers reach the defense** (`Game._applyDefensiveModifiers`, `DEFENSE_MODIFIERS_ENABLED`). Team defense ratings come from `deriveDefenseFromRoster()`, which reads **profile** attributes and is only called at roster setup, and the per-defender lookups in `runPlay`/`passPlay` read `.attributes` too — so league compression, fatigue, funding morale, disposition and form were historically **offense-only**, and `LEAGUE_COMPRESSION_FACTOR` never touched half the game. The pre-game chain now re-derives defense from `gameAttributes` after the soft cap. ⚠️ **This only helps paired with compression.** On its own it makes parity WORSE (best-record champions 28% -> 45%, Cinderella 12% -> 5%) because it also hands confidence/disposition/funding boosts to defenders, and those correlate with already being good. And compression on its own does nothing (0.7 -> 0.45 left the win spread at 22.3; even 0.25 only reached 21.4) because talent kept flowing through the uncompressed defensive channel — **this is why the earlier league-parity distribution levers all came back null.** Together (`DEFENSE_MODIFIERS_ENABLED` + `LEAGUE_COMPRESSION_FACTOR` 0.45), confirmed at 96 seasons/arm: win spread 23.1 -> 18.7 (CIs disjoint), best team's wins 25.8 -> 23.3, champion had the best record 38.5% -> 16.7%, champion from outside the top 8 (Cinderella) 6.2% -> 24.0%, most titles by one club 10/96 -> 6/96. Combined scoring RISES 29.3 -> 33.0/game; shutouts widen 5.8% -> 9.0% of team-games — distribution width, not a scoring collapse, but it is the number most likely to read as wrong to a user. ⚠️ 40-season arms materially UNDERSTATED how uncompetitive the control league is; use 8x12 for anything touching champion rank.
- **Coach influence**: `adaptability` is one-directional (`max(0, (attr-80)/20)` — below 80 has zero matchup effect); `clockManagement` gates the quality of every situational decision; `aggressiveness`/`offensiveMind` scale deep/run/medium weights. `defensiveMind` is surfaced as `coachDefMind` in play-insights (read-only context, not a weight mod).
- **Win probability** (`calculateWinProbability`): ELO prior (divisor 400) blended with a logistic score model; ELO weight decays 1.0→0.05 over regulation; time-sensitivity `k = 0.06 + gameProgress^0.8 × 0.34`; late-game possession pulls WP toward 99/1. In OT `gameProgress` is clamped to 1.0 (ELO floors, k maxes); the OT-tied FG estimate shares `fieldGoalTry`'s constants.
- **WPA → MVP / All-Pro value metric** (`_resolvePlayWpa`/`_attributeWpa` in `floosball_game.py`): per-play win-probability swing is computed on every play in every timing mode (resolved above `broadcastGameState`'s early returns) and **attributed to players** — offense to the ball-handler (run→RB, completed pass 60/40 QB/receiver, FG/XP→K), and the zero-sum defense side attributed to the **individual playmaker** (returner/sacker/interceptor/forced-fumbler/primary tackler; every on-field defender logs a snap but only the playmaker banks the swing) — NOT split across the unit, which clustered the ballot (positional mapping QB→S/RB→LB/WR→CB/TE→DE). Accumulated to `player.seasonWpa`/`seasonDefWpa` and persisted (`wpa`/`def_wpa`/`wpa_snaps`/`def_snaps` on `GamePlayerStats` + `PlayerSeasonStats`; current-season-forward, not backfillable). **Performance ratings** (`playerManager.calculatePerformanceRatings`, all 60–100, percentile-of-production scaled): `seasonPerformanceRating` = OFFENSIVE (production percentile within offensive position; kept separate for the offensive over/under metric), `seasonDefensivePerformanceRating` = DEFENSIVE (the `DEF_BOX_WEIGHTS` box composite percentile within the defensive group), and `seasonOverallPerformanceRating` = the **two-way composite** = `PERF_OFFENSE_WEIGHT (0.7) × offensive + PERF_DEFENSE_WEIGHT (0.3) × defensive` (offense-only for kickers). **MVP** runs off the overall: a flat z-score blend `mvpScore = MVP_PERF_WEIGHT (0.7) perfZ + MVP_WPA_WEIGHT (0.3) offenseWpaRateZ + MVP_DEF_WPA_WEIGHT (0.2) defWpaZ`, where `perfZ` = z of `seasonOverallPerformanceRating` (position-mean-centered / league-pooled-std). Defensive PRODUCTION is already inside `perfZ` (via the composite), so there is **no separate box `defValue` term** — the only standalone defensive term is the individual defensive **clutch WPA** (`defWpaZ`). offenseWpaRate is per-snap (`seasonWpa/seasonWpaSnaps`) so volume doesn't inflate it. `defBoxZ`/`defWpaZ` are **z-scored WITHIN the defensive group using that group's own mean AND std** (per-group std is essential — a cross-group pooled std collapses every z toward 0 since DE sack-scores dwarf CB INT-scores). Both WPA terms are **per-player** (offense→ball-handler, defense→playmaker), so neither clusters. Defense is **secondary** (30% of the perf composite + the small WPA term) so offense gates the top, but a two-way standout climbs and a one-dimensional offensive star can be edged. **All-Pro** is a single **six-player** team selected at season end (`seasonManager._selectSeasonAllPro`): the top `mvpScore` per offensive slot (QB/RB/WR/WR/TE/K) — so **defense now influences who makes All-Pro** via `mvpScore`, though there's still **no separate defensive squad** (`playerManager.selectAllDefense` unused for All-Pro). Stored as `Player.all_pro_seasons` (single accolade per honoree) + a `Season.all_pro_team` JSON (`[{id,side,position,value}]`, all `side:'offense'`) for durable recap rebuild. There is **no separate DPOY or All-Defense award** (removed — folded into All-Pro). Weights in `constants.py` (`MVP_*_WEIGHT`, `DEF_BOX_WEIGHTS`, `DEF_PLAYMAKER_BONUS`, `WPA_PASS_QB_SHARE`). Full design + build log: `docs/WPA_MVP_PLAN.md`.
- Game length is purely **clock-driven**: the loop runs `while not isGameOver()`, and `isGameOver()`/`advanceQuarter()` key only off `gameClockSeconds <= 0`. The old play-count model is **deprecated** — there is no per-game play cap; `GAME_MAX_PLAYS`/`PLAYS_TO_*_QUARTER`/`FOURTH_QUARTER_START` no longer govern flow (the `PLAYS_TO_*` ones are imported but unused) and the emitted `playsLeft` field is vestigial. Don't treat plays-per-game as meaningful.
- Balance constants live in `constants.py` / `game_rules.py` (e.g. `LEAGUE_COMPRESSION_MEAN=84`, `LEAGUE_COMPRESSION_FACTOR=0.45`, quarter length 900s, OT 600s). `LEAGUE_COMPRESSION_MEAN` is the **primary scoring dial** — it's the effective baseline every player plays at (compression only touches the live `gameAttributes` copy, not profile ratings), so raising it lifts league-wide offense (~+0.2 pts/team per point). Raised 80→84 to recover scoring the parity attribute remap cost (~33→~36 total pts/game) without re-inflating displayed ratings.

### Players, Teams, Coaches
- **Roster = 6 slots**: `qb, rb, wr1, wr2, te, k` (`team.rosterDict`). Slots are `None` when vacated (cut / unre-signed expiry / retirement).
- **Player tiers** by `playerRating`: TierS ≥92, A ≥84, B ≥76, C ≥68, D <68 (5/4/3/2/1 stars).
- Players carry offensive + derived **defensive** attributes (offense pos → defensive pos: QB→S, RB→LB, WR→CB, TE→DE, K→none) and mental/personality attributes (attitude, focus, instinct, creativity, resilience, selfBelief, pressureHandling, mood, personality, quirk).
- Contracts: `term` / `termRemaining`; `willRetire` is pre-decided in-season at the **START of week `GM_ACTIVE_WEEK`** (the moment the Front Office opens) by `_evaluateRetirementCandidates`, then executed in the offseason. The week-22 Front Office open block (retirement roll + FA retirements + supply top-up + fan-count snapshot) runs **once per season**, gated `>= GM_ACTIVE_WEEK and not _frontOfficeProcessed()` (NOT `== week`) — keyed off the persisted `front_office_fan_snapshot` marker — so a restart/deploy at or after week 22 still fires it (on the replayed week 22 or the next week) without re-rolling (`_evaluateRetirementCandidates` re-rolls every not-yet-flagged player, so the marker is what keeps the retiring set from inflating). Retirement odds are **longevity-relative**: bands key off `yearsPast = seasonsPlayed − longevity` (NOT absolute seasonsPlayed, which can't exceed league age). `playerManager.computeRetirementOdds(player)` is the single source of truth for eligibility + probability, shared by both the roll and the displayed risk tier (`computeRetirementRisk`) so they never drift. Phased contract gate: a vet only enters retirement territory on their walk season (`termRemaining==1`), but once ≥ `RETIREMENT_MIDCONTRACT_YEARS_PAST` (3) seasons past longevity they retire mid-contract too. Bands/chances in `constants.py` (`RETIREMENT_YEARS_PAST_*` / `RETIREMENT_CHANCE_*`). **Free agents** retire on a separate path (`_processFreeAgentRetirements`, keyed on `freeAgentYears`) that ALSO runs at week `GM_ACTIVE_WEEK` (with `preIncrement=True` to anticipate the offseason FA-years bump) — retirees are removed there, not just flagged, so the FA pool is finalized before ballots. By week 22 the full post-retirement picture is known (rostered flagged + FAs removed + rookie class known since season start), which the position-supply floor keys off.
- **Coach** has 8 attributes (offensiveMind, defensiveMind, adaptability, aggressiveness, clockManagement, playerDevelopment, scouting, attitude), all 60–100, neutral at 80. Per-team 3-candidate hiring slates (`CoachCandidate`).
- **Hall of Fame** (`playerManager.inductHallOfFame`, offseason training/HOF step): retirees are scored by `_computeHofPoints` (MVP 12 / ring 10 / All-Pro 4 / career-record 18 / season-record 6 / game-record 2 / 10+ seasons 4 / 14+ seasons 4) and inducted at `HOF_INDUCT_THRESHOLD` (22). Self-healing (scans newly-retired ∪ persisted retirees, skips `is_hof`). Induction stamps `player.hof_season` (the just-ended season → "Class of Season N"; null for pre-existing inductees). `hallOfFame` repopulates from `is_hof` retirees on load. Served enriched (awards, induction class, HoF credentials, position career highlight, team accent) via **`GET /api/hall-of-fame`**; the frontend renders a plaque gallery grouped by induction class (`HallOfFame.tsx`, under the Players page "Hall of Fame" tab), not the regular stats table.
- **Overall-rating formula is uniform across positions**: `(skillRating×3 + playMakingAbility + xFactor)/5`, computed identically in `updateRating` (profile) and `updateInGameRating` (the live `gameAttributes` copy). Only `skillRating` itself is position-specific. QB used to be the exception — it inherited `CachedRatingMixin`, whose `(skill×2 + playMaking×1.5 + xFactor×1.5)/5` applied to the PROFILE path only, so a QB's stored `player_rating` was not the rating they played at (mean +2.5 inflated, max +8, 4.2 places of rank noise across 43 QBs, different top-5s). Since `POSITION_VALUE` pays QB the top multiplier, the front office was paying its biggest premium off the one wrong number. Fixed by dropping the mixin; ratings recompute from attributes on load (`playerManager` calls `updateRating()`), so no migration or backfill was needed.

### Fan-Voted Awards — MVP & Hall of Fame (`awardsManager.py`, `award_repository.py`)
MVP and HoF are **fan-voted**; the value-metric MVP and the HoF-points induction become the *shortlister* and the *below-quorum fallback*. Full plan: `docs/AWARDS_VOTING_PLAN.md`.
- **Storage**: `AwardVote` (league-wide — no team scoping; MVP = one pick per user, HoF = approval, one row per approved player) + `HofBallotEntry` (rolling ballot state). `AwardVoteRepository` / `HofBallotRepository`. Voting is **free**.
- **MVP**: ballot = top `AWARD_MVP_BALLOT_SIZE` (5) players overall by `mvpScore` (not per-position; **kickers excluded** — All-Pro-eligible at their own slot but never MVP). Single-vote plurality (ties → `mvpScore`). Resolved in `seasonManager._selectSeasonMVP` via `AwardsManager.resolveMvp`; below `AWARD_MVP_QUORUM` (3) distinct voters → top-`mvpScore` fallback. Window opens at regular-season end, closes at the season-end MVP announcement.
- **HoF**: ballot seeded at the **START of week 22** (`_seedHofBallot`, immediately after the retirement roll in the Front Office open block, so the willRetire set is already populated — `_generateCoachCandidatesForFA` runs alongside it) from the just-locked `willRetire` set (final there — `willRetire` is never reversed), pre-filtered by `_computeHofPoints ≥ AWARD_HOF_BALLOT_PREFILTER` (10), and **excludes `is_hof`**. Rolling ballot: tenure `AWARD_HOF_BALLOT_TENURE` (5 seasons), then dropped. Resolved at the offseason `training` step (`AwardsManager.resolveHofInductions`): approval vote, induct top vote-getters clearing the floor (`ceil(voters × AWARD_HOF_APPROVAL_FRACTION=0.5)`), **capped at `AWARD_HOF_CLASS_CAP` (5)**; below `AWARD_HOF_QUORUM` (3) voters → **slam-dunk-only** auto-induct (`_computeHofPoints ≥ AWARD_HOF_AUTO_INDUCT_POINTS` 40 — multiple MVPs/rings/records; merely-qualified players stay on the rolling ballot for a future season's vote rather than getting a free pass), capped. `inductHallOfFame(excludePlayerIds=…)` then runs as a points-≥22 **safety net for NOT-on-ballot retirees only** (first-deploy/straggler backfill; dormant on an ongoing sim). Inductions (both the ballot path via `_induct` and the safety net) log a `hof_induction` recap event so the Season Recap's Hall of Fame list shows them. Seeding is deploy-resilient (runs any week ≥ 22, idempotent).
- **Quorum scales with engagement** (`AwardsManager._quorum`): required distinct voters = `max(floor, ceil(activeUsers × AWARD_QUORUM_ACTIVE_FRACTION=0.20))`, where the floor is `AWARD_MVP_QUORUM`/`AWARD_HOF_QUORUM` (3) and active users = the recent-login + engaged base (`anomalyManager._countActiveUsers`, same as the anomaly threshold). So a bigger league needs more turnout (50 active → 10, 140 → 28); small leagues / sims sit at the floor of 3.
- **Tallies hidden while a window is open** (no bandwagoning) — the ballot endpoints return counts only after close. **Quorum override for testing**: `AWARDS_LOW_QUORUM=1` env (or test/`_isTestMode` modes) drops the quorum to 1.
- **API**: `GET /api/awards/status` (nav window-state), `GET/POST /api/awards/mvp/{ballot,vote}`, `GET/POST /api/awards/hof/{ballot,vote}`. Windows derived from season position (no persisted flag).
- **Frontend**: dedicated `/awards` page (`AwardsPage.tsx` + `useAwards` hook) with MVP/HoF tabs; HoF cards reuse the plaque styling (award badges, team icon, stars, records-held hover). Sidebar shows the Awards entry only while a window is open.

### Card System (`cardManager.py`, `cardEffects.py`, `cardEffectCalculator.py`)
- **Editions** (rarity, ascending): `standard → base → holographic → prismatic → diamond`. Edition IS the effect tier — each effect belongs to exactly one edition (`EFFECT_EDITION_TIER`). Base = simple/reliable; higher = more conditional/synergy-dependent with higher ceilings. **`standard`** is the fusion sub-base **NO-EFFECT floor print** (`effectName:'none'`): one per player (threshold 0), it just fields the player for their FP — kept OUT of paid pack pools (`EDITION_BASE_WEIGHTS['standard']=0` + excluded from the openPack pool) and distributed as the starter/floor lineup (`auth._provisionStarterPack` grants one `standard` per position). No-effect cards are exempt from the equip no-duplicate-effect rule; `computeEffect` no-ops silently on `none`/blank.
- **Pack types** (current seed, `card_repositories.py` `seedDefaults`): `humble` 40F (reveal 3/keep 2), themed position/output/**rookie**/team packs 60F (3/2), `grand` 70F (5/3), `themed_champion` / `themed_allpro` 85F (5/3, guaranteed holo+), `exquisite` 100F (7/4). Price ladder is monotonic by value: humble < themed < grand < champion/all-pro < exquisite. `starter` is free, once/season. **There is no "proper" pack.** Paid packs share rarity weights ~{base 76, holo 32, prismatic 8, diamond 2} (team packs ~{70/23/6/2}) — ~36% non-base drops. Team packs aren't upserted, so `_seedTeamThemedPacks` refreshes their cost + weights on existing rows.
- **Effect assignment is PLANNED per bucket, not rolled per card** (`cardManager._assignEffects`, consumed by `generateSeasonTemplates` + `generateRookieTemplates` via `forceEffect`). `buildEffectConfig` picks with `random.choice`; using that independently per template both starved and clustered the pool. Measured on a live season: **31 of 143 effects had no template anywhere** (prismatic RB gave any one effect a 74% chance of not existing, diamond TE 92%) while 27 effects held 5+ templates — a card could be built, seeded, and still be unobtainable. Two rules now: (1) effects are **dealt** from a shuffled pool so every one is handed out before any repeats; (2) where a bucket has **fewer players than effects**, it mints one template per EFFECT and cycles the players. Rule 2 is what makes coverage a guarantee — dealing alone cannot help a bucket of 7 RBs carrying 27 effects, and a per-edition pooled dealer was tried first and only moved absence 35→22. A bucket mints `max(len(players), len(effects))` templates: **566 → 722** for a 32-team league, with 142 of 143 effects minted. `topUp=False` drops rule 2 and is what the ROOKIE path uses, since it supplements a pool whose coverage is already guaranteed. `effectPoolFor(edition, position)` in `cardEffects.py` is the single definition of the mint pool, shared by the planner and the roller so they cannot drift.
- ⚠️ **A bucket with NO eligible player still mints nothing**, and that is a rating-curve fact rather than a minting one. Nothing has ever rated 90 at **QB** (max 87) or **K** (max 88), and diamond's threshold is 90 — so all 13 diamond QB effects and all 14 diamond K effects (incl. **Alchemy**, the sole K-exclusive diamond) are unmintable. Owner call 2026-08-07: **left as is**; diamond stays RB/WR/TE-only until the rating curve moves. `test_effect_supply.py` asserts nothing is *intermittently* missing and that anything permanently missing has no qualifying player, so this stays visible instead of being mistaken for the sampling bug returning.
- **Packs and the shop avoid repeating an effect.** `_weightedDrawDedup(dedupByEffect=True)` now covers **every** pack (it existed but only the starter pack used it), including the guaranteed-rarity branch, which used to drop to a plain weighted draw for the remaining cards — so the pack you pay extra for was the likeliest to repeat itself. Filtering always falls back rather than returning a short pack. The shop's featured picker had a duplicate guard that **never ran**: it read `.get('effect')` where the config key is `effectName` (FACILITY_CATALOG legitimately uses `effect`, which is where the confusion came from).
- ⚠️ **Templates are minted once per season and never re-minted** (`generateSeasonTemplates` returns early when `countBySeason > 0`). A restart does **not** pick up newly-added effects — only a fresh DB or the next season boundary does. This is why a newly-built card appears to be missing from packs after a deploy.
- **Themed-pack pool filter** (`cardManager._applyThemeFilter`, keyed on `PackType.theme_type`): `position` (by position), `output` (by `output_type`), `team` (by `team_id`), `rookie` (`is_rookie==True` — the current season's draft class; the pool is already `getBySeason(currentSeason)` and veterans regenerate with `is_rookie=False`, so no season math needed), `champion`/`allpro` (dynamic, from prior-season snapshots; guaranteed holo+ since those classifications only stamp non-base). The **Rookie Pack** (`themed_rookie`, 60F, 3/2, no guarantee — the rookie classification stamps every edition incl. base) rotates in the shop via `ROTATION_CATEGORY_WEIGHTS['rookie']` and is viable whenever ≥`cards_per_pack` rookie templates exist.
- **Classifications** (on templates): `rookie` (any edition); `mvp`/`champion`/`all_pro` (holo+ only), can compound (e.g. `mvp_champion`).
- **Operations**: open packs (reveal-then-keep flow), sell, promote, blend ("The Combine"). `transplant` is a reserved `CardUpgradeLog.upgrade_type` value with **no implementation**.
- ⚠️ **The equipped lineup is SIX position-locked base slots plus FLEX** (`cardManager.FUSION_BASE_SLOTS` = `QB/RB/WR1/WR2/TE/K`, `FLEX_SLOT` seventh) — the fantasy/cards fusion made the equipped cards BE the fantasy roster, so each slot is tied to a position and `cardFitsSlot` validates it. Locked while games run. **FLEX** unlocks when an MVP-classified card is equipped OR an active `temp_card_slot` (Accession) powerup is held. Anything asking "is this a full lineup?" must count `len(FUSION_BASE_SLOTS)`, not a literal — the Gilded achievement was left on a hardcoded 5 (a full set BEFORE the fusion) and fired on a lineup with an empty slot.
- **Two-pass calculator**: first pass computes all normal effects; second pass computes cross-card effects (`copycat, chain_reaction, bonus_round, double_down, last_resort, high_roller, fortitude, charmed`) against first-pass breakdowns. Card-bug investigations: use the `card-effect-investigator` agent.
- **Effect values are FROZEN at mint** (sharp edge for balance retunes). A template's numeric params (e.g. `perRookieFP`) are computed by `cardEffects.buildEffectConfig` at template-creation time and stored in `card_templates.effect_config` JSON; both live scoring and projection (`calculateWeekCardBonuses`, shared by `cardProjection`) read the **stored** value, not the current builder. The calculator only rebuilds stored params when a **key is missing** (unresolved `{placeholder}` in the detail — `cardEffectCalculator.py:624`); a param that merely changed *value* is never refreshed. So editing a builder constant only affects **newly-minted** templates. Because templates regenerate every season (`season_created`) and **only current-season cards can be equipped/score** (`main.py:9489`), a balance change deployed at the **season boundary** (the `next-season` cutover) lands uniformly on all scoreable cards with no migration — but a **mid-season** deploy leaves that season's already-minted cards on their old value. To re-value already-minted cards in place, rewrite `effect_config.primary` in the DB (reproduce the mint-time `_RATING_DAMPENING`; `rebuildPrimaryParams` alone uses the RAW rating and will not match).

### Pick-Em System
- Predict each game's winner. **Per-game locking** — a pick is editable until that game hits Final.
- `points = base(10) × timing_multiplier × underdog_multiplier` (correct picks only). Timing decays by quarter (pre-game best, Q4/OT worst), softened for close games. Underdog multiplier from pre-game ELO (underdogs up to 3.0×, obvious favorites floored at 0.4×).
- `auto_pick_mode` on `users`: `off | favorites | underdogs | random` (auto-picks tagged `is_auto`, never overwrite manual). ⚠️ **`users.auto_pick_never_against_favorite`** (model + inline migration) is a LOYALTY OVERRIDE applied in `_autoPickFavorites` **after** the mode has chosen, so it beats every mode including `underdogs` and `random` — but only ever flips the pick TO the user's own club, never against anyone else's. Opt-in, because it loses points on average, and surfaced only to a user who HAS a favourite team. Clairvoyant bonus when weekly points exceed `PICKEM_CLAIRVOYANT_THRESHOLD`.
- **Whole-day picks**: `GET /api/pickem/day` returns every slot of the current calendar day (each slot labeled `Week N`, with its games + the user's picks — **no modifiers**, those live on the fantasy page) so a once-a-day user can prognosticate the full slate at once; `POST /api/pickem/picks` bulk-submits `{week, gameIndex, pickedTeamId}` across slots (per-game lock still applies — Final games are skipped, not errored). Per-game `/api/pickem/pick` is unchanged. `_buildPickemMatchup` is the shared matchup serializer.

### Anomaly System (`anomalyManager.py`)
A per-player "attention" score (decays 10%/week, fully **user-generated** — equipped cards [which ARE the fusion fantasy lineup, weight folds in the retired separate fantasy-roster source]/follows/favorite-team fans, no sim source) feeds a per-player ladder (`stable → stirring → erratic → rampant → awakened → cleansed`) and a hidden per-season league aggregate (`over_cap_carry` sum + linear background pressure) that can trigger league-wide "thinning"/Cores events. Surfaced via `/api/players/{id}/anomaly`, `/api/debug/anomaly-*` (testing aids — **not admin-gated**), and `league_news` items.
- **Aggregate is a LEAKY INTEGRATOR** (`_applyDecay`): each weekly tick decays both the per-player `score` (`ATTENTION_DECAY` 0.9) **and** its accumulated `over_cap_carry` (`OVER_CAP_CARRY_DECAY` 0.82, non-FAST). Carry decay is what stops the aggregate being a monotonic accumulator — it plateaus at a level proportional to CURRENT sustained attention (≈ weeklyOverflow/(1−decay)) instead of ramping unbounded over the season. (Historic bug: without it, a loaded league's aggregate ran to many× the bar and stayed **pinned critical**, re-crossing every suppression window.) FAST mode leaves carry undecayed (1.0) so sims still ramp and trigger.
- **Adaptive threshold** (`_maybeSeedAdaptiveThreshold`, prod/non-fast): the hidden bar is seeded from the league's **own emergent attention**, not a user-count guess. Weeks 1..`THRESHOLD_SEED_WEEK`−1 (6) are a quiet calibration window (bar = `THRESHOLD_PROVISIONAL` sentinel, no crossings); at the seed week the plateau is estimated from the observed aggregate (`overcap / (1 − carryDecay^week)`) and the bar locks at `THRESHOLD_PLATEAU_MULT` (0.92) × plateau, floored at `THRESHOLD_FLOOR` (120, so a barely-engaged league never trips). Self-normalizes to any league size (attention concentrates on the fixed 24×6 pool, so the aggregate scales super-linearly — a linear user-count formula, the old `THRESHOLD_BASE + PER_USER×activeUsers` approach, mis-scaled it and pinned large/concentrated leagues). Tuned against a realistic-attention Monte-Carlo harness: ~1.5-3 Criticalities/season with ~90-100% odds of ≥1, no pinning, across 29/60/140-user leagues. FAST mode keeps the old low random band (`THRESHOLD_MIN/MAX`). Legacy `THRESHOLD_BASE`/`THRESHOLD_PER_ACTIVE_USER`/`THRESHOLD_JITTER` are unused now (`_countActiveUsers` still powers award/anomaly quorums).
- **Criticality gating + admin toggle** (`ANOMALY_CRITICALITY_ENABLED` default False, overridable live via the `criticality_enabled` app-setting from the admin panel): while OFF, a crossing never fires the real "thinning" — it's dramatized as a near-miss/suppression (the season is a tease, but the buildup is **not silent**). While ON, a crossing rolls to fire (see the fire-roll bullet).
- **Instability dial** (`getCriticalityMultiplier` / `_instabilityMultiplier`): the per-play glitch multiplier (used in `floosball_game._maybeFireAnomalies` as `prob = (attention/SCALE) × multiplier`) rides the aggregate's approach to threshold — flat at `INSTABILITY_BASELINE` while quiet, ramping to `INSTABILITY_PRECRIT_CEILING` (< `CRITICALITY_MULTIPLIER`) as the ratio climbs from `INSTABILITY_RAMP_START`→1.0, and floored to `INSTABILITY_SUPPRESSED` during a suppression window. So glitch frequency breathes with league tension.
- **Fire roll + pity ramp** (`_triggerCriticality`): when enabled, a crossing FIRES with probability `CRITICALITY_FIRE_CHANCE` (0.30) and otherwise suppresses (near-miss). To stop an unlucky streak whiffing a whole season, the odds **escalate**: each fire-eligible suppression since the last real fire adds `CRITICALITY_FIRE_CHANCE_RAMP` (0.25, capped at `CRITICALITY_FIRE_CHANCE_MAX` 1.0), so the event is bounded to land within a few crossings while the first crossing stays at the base rate (`_eligibleSuppressionsSinceLastFire`; resets on a fire). Only ENABLED crossings accrue pity — gated near-misses carry `fire_eligible:False` and never count, so a season spent disabled doesn't hand you a guaranteed instant fire the moment you flip it on.
- **Suppression / near-miss beat** (`_suppressCriticality`): a crossing that doesn't fire (gated OR an enabled fire-roll that lost) — record a `suppression` entry on `cores_patches_applied` (tagged `fire_eligible`), open `suppression_window_ends_week` (= week + `SUPPRESSION_WINDOW_WEEKS`), drain every player's `over_cap_carry` toward `SUPPRESSION_TARGET_RATIO × threshold` (so the aggregate genuinely re-climbs), bump `threshold` by `SUPPRESSION_THRESHOLD_BUMP`, re-arm the warning cycle, and broadcast a Core-attributed line. **Uncapped** (no `SUPPRESSION_MAX_PER_SEASON` — removed): with carry decay the aggregate no longer stays pinned, so the Cores can keep catching every non-firing crossing all season.
- **Status** (`getCriticalityStatus`): number-free qualitative bands (`dormant/stirring/unstable/critical`, or `stabilizing` during a window) for the Cores control-room view. The band is derived from a **LIVE carry sum** (`_sumOverCapCarry` + week pressure), NOT the stored `aggregate_score` — the stored value is only rewritten on the weekly tick / reset / suppression, so after a Criticality resolves (Reset drains the carry but leaves the pre-drain aggregate persisted) it would otherwise pin the status on `critical` until the next tick. When the stored value has drifted from live, the status read **self-heals** it (writes the recomputed aggregate back), so the glitch dial recovers too. Public via **`GET /api/cores/status`** (no raw aggregate/threshold — those stay in the ungated debug endpoint). Regression: `test_anomaly_suppression.py`.

- **Multi-Core exchanges** (`_EXCHANGES`, `exchangeEntriesFor`/`entriesForEvent`) — short conversations for the louder beats (`warning_high`, `suppression`, `criticality`) plus `idle` ambient banter. Each turn broadcasts as its own `cores` news item sharing an `exchangeId` + `turnIndex`/`turnCount` so the feed threads them. `entriesForEvent(event)` auto-picks exchange-where-it-exists, else solo; a forced `core=` always yields one attributed line.
- Ambient banter for the control room: **`GET /api/cores/conversation?event=idle`** (ephemeral, not persisted). `idle` may surface a **live data-aware beat** (`CORES_DATA_BEAT_CHANCE`, default 0.5); `event=observe` forces one. Data-aware beats are generated from live state — `observationExchange`/`observationEntriesFor` (real aggregate/threshold/percent + named climbing/awakened players) and `gameResultExchange`/`gameResultEntriesFor` (real teams/scores: nail-biter, upset, shootout, blowout). **These reference RAW numbers on purpose and live ONLY in this ephemeral control-room endpoint** — the public header/news feed stay number-free (`getCriticalityStatus`). The API layer gathers state (`_gatherAnomalyObservation` / `_gatherRecentGameResults` in `main.py`); coresManager owns the voicing.
- **Instance 498b**: this floosball is catalogued (Cores-side) as `498b` — `498a` is the prior failed iteration of the same instance; a Reset that doesn't hold burns the letter (`→ 498c`). The number is a Cores-only label (players never say it); it surfaces in idle banter + a `warning_high`/`reset` beat or two. Full lore in `data/lore.md` "Instance 498b".

### Personality & Reactions
`personalityManager` (YAML-templated personalities, quirks, moods, quotes) + `personalityReactionEngine` (in-game reactions, sideline cutaways surfaced in `game_state`/play insights). `rallyManager` handles live fan rallies (`POST /api/games/{id}/rally`).

### Discord Integration
Link via `/api/bot/link` (short-lived code → `users.discord_id`); opt-in DM reminders (`discord_dm_reminders`). Bot endpoints (`/api/bot/*`) authenticate with an **`X-Bot-Key` header** shared secret (`_checkBotAuth`), not Clerk. The bot itself is a separate Node/discord.js repo at `../floosball-bot` (commands auto-load from `src/commands/`; `npm run deploy-commands` registers them with Discord).
- **Name submissions** (`/name` slash command → `POST /api/bot/names`): a Discord-**linked** user suggests a player name. It does NOT enter the pool — it lands in `name_submissions` (status `pending`) for admin review on the Admin page's Names tab (`GET /api/admin/names/submissions`, `POST /api/admin/names/submissions/review` with `{ids, action}`). Approving runs the name through `_acceptNamesIntoPool` — the SAME vetting as a direct admin add — so the two paths can't drift; a name that got taken while queued is reported back and left pending rather than silently dropped. **Rejected rows are kept, not deleted** (unique `name`), which is what stops a name being resubmitted on a loop. Per-user cap on pending rows: `NAME_SUBMISSION_PENDING_CAP`. Regression: `test_name_submissions.py`.

## Database
- SQLite at `data/floosball.db`. **62 SQLAlchemy models** in `models.py` (domains: game/season/stats, players/attributes, user/economy, cards, fantasy, pick-em, shop, achievements, GM, awards voting, team funding, anomaly, misc). `grep "class .*(Base)" models.py` for the list.
- **Two migration systems**: `alembic/versions/` (~38 files, canonical schema history for local/fresh setups) and **inline migrations** in `connection.py::_runPendingMigrations()` (idempotent `ALTER TABLE ADD COLUMN` / `CREATE TABLE IF NOT EXISTS`). **Inline migrations are what runs in prod** on every boot — alembic is not auto-run on deploy. New columns need an inline migration to land on existing prod DBs.
- `init_database()`: create_all → inline migrations → seeds (`_seedPackTypes`, `_seedBetaAllowlist`, `_seedAchievements`, `_seedUnusedNames`) → backfills (funding tiers, player season/career stats from games, team peak streaks, card output types).
- `clear_db()` (fresh start) **preserves** `users`, `beta_allowlist`, `app_settings`, `unused_names`; nulls per-season user flags (`starter_pack_claimed_season`, `favorite_team_locked_season`). After fresh start, existing users get re-provisioned starter packs in `startNewSeason()`.
- ⚠️ **A finished game keeps its box score, not its plays** (owner, 2026-08-09). `GET /api/games/{id}` now carries `boxScore`, rebuilt from `game_player_stats` by `game_box_score.buildBoxScore` — those rows were always written and simply never read, so a week-1 game 24 weeks later answered 200 with the right score and no stats. The endpoint also falls back to `buildFinishedGame` when a game is not in memory (it used to 404), so a game survives a restart. **Play-by-play is deliberately NOT persisted** — it lives only on the in-memory game object, which is the intended trade.
- ⚠️ **The quarter line was never written until 2026-08-09.** Both save paths guarded on `game.homeScoresByQuarter`, a LIST attribute the game object has never had, so `hasattr` was always False and every quarter column stayed 0 — measured at **0 of 783** finished games, with nothing ever raising. The engine accumulates `homeScoreQ1..Q4` / `homeScoreOT` (`floosball_game` ~:12308). Now 352/352 and each line sums to the final.
- **Playoff runs are DERIVED, not stored** (`playoff_history.py`, `GET /api/teams/{id}/playoff-history`): `games.is_playoff` + `playoff_round` already record every postseason game, so a club's depth per season is recoverable — including for seasons that predate the endpoint, which a stored column could not do. Rounds map 1→R1, 2→R2, 3→League Championship (CR), 4→Floos Bowl. Regression: `test_game_history.py`.
- ⚠️ **`games.team_stats`** (JSON): the full per-team box score at completion — `{'home': {...}, 'away': {...}}`, the same `team` block `_buildGameStatsSnapshot` broadcasts live. Written by `seasonManager._applyTeamStatsToRow` on **both** completion save paths, read by `api.main._teamStatsFromRow`. The dedicated `home_`/`away_` columns are **not** superseded and were **not** enough: they cover yards/TDs/FGs/sacks/ints/fumble-recoveries, but **first downs and third/fourth-down conversions have no column and are NOT derivable from `game_player_stats`** — a first down is a team event with no player row to sum. A blob on the existing row rather than a `game_team_stats` table, since this is display data that is never aggregated over (season totals have their own table), so a join buys nothing and a second row per game costs more than the JSON. **NULL means "never recorded", NOT "all zeros"** — `_teamStatsFromRow` returns None and callers must OMIT the key, or a card states a real game had no first downs. Not backfillable. Surfaced on `GET /api/games/{id}` (live object first, blob as fallback) and `GET /api/weekGames`, which is what lets a past-week board card show how the two clubs compared. **Play-by-play remains deliberately unpersisted** (owner, 2026-08-09) — the feed is far larger than these totals.
- **`games.format_state`** (JSON): the per-format box-score breakdown that has no dedicated columns — the innings line score, frames results, chess-clock budgets — i.e. whatever `GameFormat.stateExtra()` emits. Written at completion by `seasonManager._applyFormatStateToRow` (both the UPDATE and INSERT save paths). It's computed live and rides the `game_state` WS broadcasts, so without persisting it a finished game rebuilt from the DB has no source for it. `GET /api/games/{id}` prefers the live in-memory state and falls back to this column. NULL for standard games (their breakdown is the quarter-score columns) and for anything finished before the column existed — **not backfillable**, the state only ever existed in the live stream.
- Repositories in `database/repositories/`: base (Player/Team/League/Game/Record/UnusedName), card (`CardTemplate/UserCard/EquippedCard/Currency/PackType`), game (`Game/GamePlayerStats` — note a second `GameRepository` exists in both `base_repositories.py` and `game_repository.py`; the app uses the latter), gm, notification, pickem, shop. For new columns, follow the `/migrate` command's four-step pattern (model → inline migration → backfill → load/save plumbing).

## Deployment (Fly.io)
```bash
fly deploy                                                 # Normal deploy (resumes season)
fly ssh console -C "touch /data/.fresh" && fly deploy      # Fresh start (one-shot flag file, auto-deletes on boot)
```
- `TIMING_MODE` in `fly.toml` `[env]` — normally `scheduled`; use `fast-catchup` to recover missed games.
- Prod SQLite at `/data/floosball.db`, **no `sqlite3` binary** — query via a `python3` heredoc in `fly ssh console` (use the `/dbquery` command).
- Never use the `FRESH_START` env var in prod (it survives restarts and would wipe the DB on outage recovery). `FRESH_START` is a local-dev-only convenience.

## Open Questions / Known Quirks (verified 2026-05-31, unconfirmed intent)
- **`rating_cache.py` is dead code**: `CachedRatingMixin` was removed with the QB rating fix (it was the sole cause of the profile-vs-in-game divergence, and PlayerQB was its only consumer). What remains — `RatingCalculationCache` — is reachable only via `service_container`'s `registerFactory('rating_cache')`, which builds an instance nothing ever reads and whose shutdown path calls a method name that doesn't exist (`cleanupExpiredEntries` vs `cleanup_expired_entries`, swallowed by a bare `except`). Safe to delete the module and its three `service_container` references; left in place pending a call.
- **QB rating predicts wins WORSE than RB/WR/TE**, and the rating fix above did not change that. Measured post-fix over 2,560 team-seasons (8 fresh 32-club leagues × 10 seasons): corr(position rating, team wins) = WR +0.451, RB +0.368, TE +0.273, QB +0.253, K +0.123. (The WR figure averages two starters, so its noise is lower and it is not like-for-like with the single-player positions; QB vs RB vs TE is the fair comparison.) So the QB-vs-RB gap is NOT a measurement artifact of the divergence bug — it is a real property of the sim, and `POSITION_VALUE`'s QB 1.00 top multiplier is unexplained by rating quality. Caveat: no matched pre-fix arm was run on this league size, so the ordering is solid but the fix's delta is not measured.
- **`/api/debug/anomaly-*`** are not admin-gated (comment says intentional for local sims, "not for production users"). Not gated in prod.
- **Dead/legacy**: the play-count model (`GAME_MAX_PLAYS`, `PLAYS_TO_THIRD/FOURTH_QUARTER`, `FOURTH_QUARTER_START`, the `playsLeft` output) is deprecated — game length is clock-driven; `timingManager.shouldUseInGameDelays()` has no callers; `auto_pick_favorites` column is superseded by `auto_pick_mode`; `players.demeanor`/`archetype` columns are legacy-nullable; `registerSingleton` in `service_container.py` doesn't actually cache (behaves like `registerFactory`).
